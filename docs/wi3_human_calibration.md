**定性メモ（原文ママ）**: 「やってみたけど全体として同じと感じる曲はなくテンポや
トーンから似てると感じる基準で評価した」

### 判読（3 つの核心）

1. **作品同一性は MusicGen レンダリングで人間の耳からも消失している**。
   同一スコア・同一プロンプトの再生成ペア（p01）ですら「別の曲」判定であり、
   yes は全て低確信（1–2）。「同じ曲」と感じたペアはゼロ（定性メモ）
2. **人間の「同じ」は出所でなく音響的同質性を追跡する**。同一セル A-A が no で
   別スコアの病理対 A3-C3 が yes — provenance と知覚が乖離しており、この素材では
   「同一作品か」という校正質問自体がほぼ成立しない
3. **クロス演奏者の同一作品（p09）が no** — 「楽譜を運べば作品が運ばれる」は
   この演奏者対（決定論 synth ↔ MusicGen）では人間知覚レベルで不成立。
   人間が使った手がかり（テンポ・トーン）は計器の物理軸と同じものであり、
   計器が間違った軸を測っているのではなく、**レンダリングが作品を運んでいない**

- **採用条件（誤り ≤1 かつ P1・P3 対照の正分類）を満たす軸は 0/5 = proxy v0 は
  空集合**。`null_results_are_valid`（事前登録 §4）に基づく有効な結果
- 誤り 3 件は全て P3 陰性対照での「same」誤予測だが、**機構は軸ごとに別物**:
  bpm/p07 = **89.1 アトラクタ**が A3 を other_work 側へ引く（WI2 §4 の弁別
  コストの人間対照での実測）/ structure/p07 = 位置整合率の**長さバイアス**
  （3 トークン観測が他作品 3 トークン参照に近く出る・WI2 §4 と同型）/
  key/p08 = **key センサーの平行調流れ**（C2/D3 双方が C major 読みで
  other_work に一致）。共通するのは「センサー病理が別作品ペアの距離を縮めて
  same に化ける」という故障モードであって、原因軸は 3 種に分かれる
- harmony / brightness は 12/12 棄権（判定材料ゼロ = 解像度不足の再確認）

### 規則の v0 限界（透明記録・事後変更なし）

- **構造的棄権の大量発生**（10–12/12）: 最小差参照セット（WI2 で交絡是正のため
  group 3 参照の bpm/brightness 宣言を同一化）× 事前登録の厳格 tie 規則
  （rank-1 が tied なら棄権）の相互作用で、group 内の rank-1 は物理軸で常に
  tie になる。事前登録どおり適用し、集計は変更しない
- **v1 改良案**（次トランシェで事前登録し直す）: rank-1 比較を参照単位でなく
  **作品単位の同値類**（同一作品由来の参照群をまとめてから tie 判定）で行う。
  距離マージン（2 位との差）の併用も候補
- 集計実装の落とし穴 2 件を記録: PyYAML が素の `yes/no` を bool 化する既知
  挙動（明示正規化で回避）/ 回答の pairNN は提示順で pair_id とは別軸
  （封印側の変換表で照合・検算アンカー全一致で裏付け）

## 4. WI 系列への含意

- **WI2 の機械側結論と合流**: 弁別フロンティア = bpm のみ（WI2）×「人間も
  テンポ・トーンでしか判定できなかった」（WI3）— 機械と人間が同じ壁を
  別々の方法で確認した。この生成器の **identity budget（WI4）は実質
  bpm 近傍のみ**であり、それすらアトラクタで漏れる
- **校正実験として成立する素材の条件が判明**: 「同じ曲」知覚が存在しない素材では
  予測力の校正は原理的に進まない。第 2 トランシェは (a) 実 Suno ペア
  （P5: 正典 form take vs 順序破壊 take — 素材回収が前提）と (b) synth 内
  スタイル変換ペア（p10 が唯一の「作品保存 × yes」）を軸に設計する
- 被覆明細: melody（#199 除外）/ lyrics / CLAP（extra 未導入）は not_observed の
  まま。n=1・非 canonical v0 につき主張強度はそれ相応
