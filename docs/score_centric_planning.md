## 1. この計画を生んだ設計判断（壁打ち結論・第三段階）

プロジェクトの重心読み替えは三段階を経た:

| 段階 | 日付 | 読み替え | 帰結 |
|---|---|---|---|
| 第一 | 2026-06-02 | パラメータは「評価する値」でなく「制御する値」 | K 系列誕生（grip） |
| 第二 | 2026-06-03 | audit は「裁判官」でなく「計器」 | verdict 排除を型で固定 |
| 第三 | **2026-06-12** | **計器は「楽譜を書くためのパラメータ取得道具」** | T 系列新設・Q 再定義 |

第三段階の中心命題:

> **AI は演奏者であり、我々が作るのは AI 世代の楽譜である。計器類（RPE 抽出・
> audit・eval）はその楽譜に必要なパラメータを取得するための道具であって、
> 正しさ・合致性は本質ではない。**

これにより RPE の主用途が「演奏後の検証（下流）」から「**作曲前のパラメータ
取得（上流）**」へ反転する。本書執筆時点では逆方向（audio → RPE → draft Score
= 採譜）が未実装で、これが T 系列の対象だった。**現在は T0/T1 が実装済み**
（`transcribe/measure.py` の `measure_fields` / `transcribe/score_draft.py` の
`draft_score` / `svprpe transcribe`、§3 T1 の Status: IMPLEMENTED 参照）。

### 1.1 「正しさは本質でない」の正確な読み方

捨てるのは **対真値 accuracy**（推定 BPM が真の BPM に一致するか）。
捨てられないのは **目盛りとしての資質**:

- **単調性** — 音楽が明るくなれば針も上がる
- **再現性** — 同一音源 → 同一の読み（決定論）
- **有効帯域** — 音楽が実際に変化する範囲で針が動く

K1 の brightness 事件（[`controllability_poc.md`](controllability_poc.md) §5.1）が
実証例: 帯域比センサーは「不正確」だったのではなく「**盲目**」だった。
「正しさ不要」を「校正不要」と読み違えると、センサー盲のまま楽譜に死んだ
パラメータを書き込むことになる。→ Q 系列は廃止ではなく校正トラック化（§4）。

### 1.2 合致性が残る唯一の場所

合致性（spec 準拠の比較）は合否ゲートとしては廃するが、**作曲家がテイクを
採るか録り直すかを判断するための計器の読み**として残る。C4 デモ
（[`composition_poc_report.md`](composition_poc_report.md) の二テイク針比較）が
既にこの使い方をしている。作品同一性
（[`ai_music_daw_vision.md`](ai_music_daw_vision.md) §7.2 の semantic 一致）も
この読みに包含される — 精緻化は本質投資ではなく、針が読めれば足りる。

## 2. 通底原理 — 双方向再現性

プロジェクトの変遷を通じて通底しているのは **RPE/SVP を使った再現性** である。
第三段階でその意味が一方向から双方向へ拡張された:

| | 旧・一方向の再現性 | 新・双方向の再現性 |
|---|---|---|
| 定義 | audio → RPE → SVP が決定論（同一入力 → 同一出力） | 楽譜 → 演奏 → 計器 → 楽譜′ の**往復でロック欄が保存される** |
| 単位 | 抽出パイプラインの決定論 | 往復の**保存性**（round-trip preservation） |
| 検証 | snapshot test | ロック欄の往復一致率 |

### 2.1 往復保存性の分解

往復保存性は二つの独立な性質の積に分解できる:

```text
往復保存性(field) ≈ grip(field) × 校正(field)

  grip   — 演奏者がそのフィールドを読んで出力に反映するか（K 系列が測る）
  校正   — 計器がその性質を目盛りとして読めるか（Q 系列が校正する）
  採譜   — 往復の帰り道そのもの（T 系列が実装する）
```

ロックしたフィールドが往復で失われるとき、原因は **ツマミ死**（演奏者が
読まない）か **センサー盲**（計器が読めない）のどちらかであり、K1 が確立した
dead の 2 分類がそのまま診断軸になる。**三トラックの存在理由がこの一式に収まる。**

### 2.2 往復保存性はスキーマの入場試験である

往復保存性は検証指標であるだけでなく、**スキーマにフィールドを追加する際の
採否基準（admission test）**として運用する:

> 新しいフィールドは、往復を生き残ること — grip があり、センサーがあり、
> 採譜で帰ってくること — を示して初めて正規スキーマに入る。

「あったら良さそう」でフィールドが増殖するスキーマ腐敗を原理一つで防ぐ。
T2 でループが立った後は、フィールド追加の Design Memo に往復一致の実測
（または実測計画）を必須項目とする。

## 3. T 系列 — 採譜トラック

採譜の粒度は **per-field 計測 → 全曲 draft Score の段階構成** とする
（2026-06-12 ユーザー判断）。派手なのは後者だが、「計器 = パラメータ取得道具」に
忠実なのは前者であり、前者が後者の部品になる。

### T0: per-field 計測ユーティリティ

**目的**: 音源 1 本から、CompositionScore の指定フィールドに転記可能な計測値を
取得する最小ユーティリティ。

| 項目 | 内容 |
|---|---|
| 入力 | 音源（WAV/MP3）+ 対象フィールド名のリスト |
| 出力 | `{field: 計測値, sensor: 使用センサー, 校正メモ}` の JSON |
| 変換表 | [`controllability_poc.md`](controllability_poc.md) §6 のセンサー対応表を**そのまま採譜変換表として再利用**（grip 測定と採譜は同じ写像の双対） |
| 対象フィールド | 現行 `PhysicalLayer` の**全 7 必須フィールド**: `bpm` / `key` / `time_signature` / `brightness`（centroid 正規センサー）/ `active_rate_target` / `valley_depth_target` / `stereo_width` |

> **必須欄の網羅**: `PhysicalLayer`（`src/svp_rpe/compose/models.py`）は全欄
> required（`extra="forbid"`）のため、T1 が loader-valid な draft を出すには
> T0 が 7 欄すべての計測経路を持つ必要がある。`time_signature` は既存の拍子検出器
> `compute_time_signature()`（beat-strength ベース、`rpe/physical_features.py`）で
> 観測する — [`validation.md`](validation.md) で 5/5 exact match（3/4 ワルツ含む）。
> `stereo_width` は audit の `ObservedRPE.metrics["stereo_width"]` 経由で観測する。
> 校正メモには針ごとの検証状態（validation 実績・既知の癖）を記録し、弱い針を
> 隠さない — それが校正トラックの流儀。

**完了基準**: 合成 5 曲に対して per-field 計測が決定論で走り、出力 JSON が
snapshot test で固定される。校正メモに既知の癖（例: bpm 高水準の検出が低めに
出る）が field 単位で引用される。

### T1: draft Score 採譜（`svprpe transcribe` 相当）

**Status**: IMPLEMENTED in `svprpe transcribe` (T1).

**目的**: 音源 1 本から CompositionScore の**下書き**を YAML で出力する。

- **物理層** — T0 の計測値で埋める
- **意味層** — **空欄（人間が書く欄）** とし、プレースホルダで明示する（§5）
- **構造層** — 既存セグメント抽出（`rpe/structure*.py`）から区間ラベルを下書き

> 楽譜には「計器で取る欄」と「作曲家が書く欄」がある — この区別を出力
> フォーマット自体が表現する。下書きはあくまで下書きであり、採譜結果の
> 無編集演奏（コピー生成）は目的ではない。

**完了基準**: 合成 5 曲から生成した draft Score が `compose/` の loader で
そのまま読める（スキーマ妥当）。意味層プレースホルダが loader で弾かれない
形式で表現されている。

### T2: 往復保存性の最小実証

**目的**: §2 の双方向再現性を初めて数値にする。

```text
既存 CompositionScore → C4 決定論的演奏者で演奏 → T1 で採譜 → 元 Score と比較
```

- 比較対象はロックしたフィールド（まず物理層のセンサー有りフィールド）
- 全区間が決定論（演奏者 = C4 シンセ、採譜 = T1）なので **in-repo テスト可能**
- 出力: field ごとの往復一致表（保存 / ツマミ死で喪失 / センサー盲で喪失 の三値診断）

**完了基準**: 往復一致表が docs に記録され、K1 の grip 地図と整合する
（grip=tight のフィールドは保存され、dead のフィールドは喪失と診断される）。
これが「ハーネスが正しく測れている」ことの相互検証になる。

### T3 以降（候補、T2 の結果を見て判断）

- **事象レベル欄への登坂**（§6 急所 1 の解消）— 旋律 / コード進行 / フックを
  書ける欄とそのセンサー。プロダクトの根本に関わるため、延期はしても省略しない
- 確率的生成器（Suno 級）での往復実験 — K2 と合流しうる
- fixity 型（ロック/アンロックのスキーマ化、
  [`controllability_poc.md`](controllability_poc.md) §8）— T1 の出力が
  「どの欄を計測値でロックしたか」を表現する受け皿として T1 の後に置く

## 4. Q 系列の再定義 — 計器校正トラック

定義の書き換え本文は [`roadmap_goal1.md`](roadmap_goal1.md) 冒頭に反映した。
要点:

- 完成の主張は「推定が真値に一致する」ではなく「**各針が楽譜へのパラメータ
  転記に使える目盛りであることが文書化されている**」（単調性・再現性・
  有効帯域・目盛りの文書化）
- **対真値比較は校正の手段として残る** — 温度計を基準器に当てる行為。
  目的（accuracy 達成）から手段（目盛り付け）へ役割が変わる
- 既存 Q0–Q5 のフェーズ表・受け入れ条件は校正作業のチェックリストとして
  引き続き有効。Q1-3（BPM 信頼度）は「この針はどこまで信用して転記できるか」
  という校正タスクとして T0 の校正メモに直結する

## 5. 意味層の扱い（現状と将来）

**現状（T1 時点）**: 意味層は採譜で埋めない。`semantic.core` に対応する
RPE 観測量が無い（[`controllability_poc.md`](controllability_poc.md) DD-D）ため、
**人間が書く欄**としてプレースホルダ化する。

**将来**: 意味層も取得変数として扱う方針（2026-06-12 ユーザー判断）。
意味層センサーの開発を視野に入れる。ただし:

- 意味層センサーは学習モデル（embedding 等）を要する可能性が高く、その場合は
  [`learned_models_policy.md`](learned_models_policy.md) の optional extra 隔離
  方針に従う（決定論コアを汚さない）
- 開発順序は **物理層の往復保存性（T2）が立ってから** — 往復の方法論が確立して
  いない段階で観測困難な層に投資しない
- 着手時は DD-D の解除条件（どの意味フィールドに、どんな観測量を、どの校正
  基準で対応付けるか）を先に文書化する

## 6. 既知の急所（2026-06-12 壁打ちで特定）

### 急所 1: 識別力ギャップ — 「曲の正体」を書く欄がまだ無い【根本的】

現行 `PhysicalLayer` のロック可能フィールド（bpm / key / brightness / 密度）は
**制作パラメータ**であり、曲を「その曲」たらしめる**音楽的事象**（旋律モチーフ、
コード進行、フック）ではない。「bpm 120・ハ長調・明るめ」を満たす曲は無数に
あるため、現状の Score は [`ai_music_daw_vision.md`](ai_music_daw_vision.md)
§7.1 条件 (3) Discriminability を満たさない — 楽譜というより**注文票
（スタイルシート）**に近い。

- **失敗モード**: 制作パラメータの往復ループが綺麗に回ることに満足し、
  「作品 = 楽譜」の同一性主張が成立しないまま完成を宣言する。**ループの成功
  自体が欄の不足を隠す**
- **登坂ルート**: 旋律 / コード進行のセンサーは MIR に既存技術がある
  （basic-pitch / chord recognition 等、
  [`learned_models_policy.md`](learned_models_policy.md) の optional extra
  隔離方針の管轄）。事象レベルの欄は §2.2 の入場試験を通して正規スキーマに入れる
- **計画上の位置**: T2 でループ確立後の本丸として T 系列の延長に置く（§3 T3 以降）

### 急所 2: grip 転移の未証明 — と「選択=制御」の保険

K1 の grip 地図は配線が既知の決定論演奏者に対する測定（自作テレビで自作
リモコンの動作確認をした状態）。本命の確率的演奏者（Suno 級）はテキスト
プロンプトしか受け付けず、楽譜は**ストロー一本**で渡される — 指示がどれだけ
削れるかは未知数で、転移の確認（K2）がコンセプトの土台に関わる。

**保険 — 選択も制御である**: ツマミ（指示）が効かない場合でも、

```text
N テイク生成 → 各テイクを計器で測定 → 楽譜に最も近いテイクを採用
```

（オーディション / rejection sampling）で制御は回復できる。これは grip 不要・
**センサーのみで成立する最後の制御チャネル**であり、§1.2 の「合致性=テイク
採用判断」の読みはこの保険を担保している。K2 で tight が出なかったツマミは
本方式の対象として扱う。

## 7. 推奨順序

T 系列内は T0 → T1 → T2 の直列依存。他トラックとの間に実装依存は無いが、
順位付けは以下を推奨する:

| 順位 | タスク | 理由 |
|---|---|---|
| 1 | **T0 → T1 → T2** | 最小工数で作曲ループが一周つながり、§2.2 入場試験の試験台が立つ。全区間が決定論・in-repo で完結 |
| 並走 | **K2（Suno 転移）** | 急所 2 の検証で実存的に重要だが、律速は手動生成バッチ（人間の作業時間）であり Claude/Codex サイクルと競合しない。機会あり次第いつでも |
| 2 | **fixity 型** | T1 の出力「どの欄を計測値でロックしたか」の受け皿。T1 後が自然 |
| 3 | **事象レベル欄への登坂（急所 1）** | 根本的だが、入場試験（T2）の確立が先。学習モデル隔離方針の確認とセンサー選定の planning から入る |
| 4 | **Q 系列の校正タスク（Q1-3 から）** | T0 の校正メモ需要に引かれて個別に復活 |
| 5 | **C5（Score 修正ループ）/ C6（演奏者 src/ 昇格）** | C6 は「標準のリファレンスレンダラー」として再評価（急所 2 の保険のテイク生成器にも資する）。判断は T2 後 |

採譜が通ると「参照曲を計器にかける → 楽譜下書き → ツマミをロック/開放して
編集 → 演奏者に渡す → 針を読んで録り直し判断」という**作曲ループが初めて
一周つながる**。
