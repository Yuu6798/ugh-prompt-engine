# LLM Adapter Planning — LLM 著述トラック (L 系列)

**Status**: L0 計画文書（2026-08-05 起案、Fable 設計セッション）。実装未着手。
L0-s（手動スパイク）から開始する。旋律軸の配線（L0c）は M2e 破断曲線と
M4 の evidence 翻訳に依存するため凍結し、非旋律軸で先行する。

## 1. 目的

生成器（Suno / MusicGen 等）の弱点である**作品としての意味的一貫性**を、
LLM が上位層で設計することで補完する構想の、実験可能化。

LLM が `CompositionScore` を著述し、決定論パイプライン（perform → extract →
compare）で検収し、構造化された差分報告に基づいて修正する閉ループを確立する。
本トラックの検証対象は「**LLM は Score という言語で作曲できるか**」であり、
生成器の実行精度（grip、K 系列）や計器の帯域（M 系列）とは分離して測る。

### 1.1 因果の鎖と本トラックの守備範囲

「LLM が意味設計で生成器を補完する」は 5 リンクの鎖に分解される:

| リンク | 内容 | 検証トラック |
|---|---|---|
| 1 | LLM が意味 → 音楽的制約（Score）を導出できる | **本トラック (L)** |
| 2 | 制約を構造化表現として書ける | 済（CompositionScore 三層言語） |
| 3 | 生成器が Score に従う（grip） | K 系列（本トラック外） |
| 4 | 出力を測って設計との差分が取れる | M 系列 / 既存センサー（本トラック外） |
| 5 | 差分から失敗箇所だけ修正できる | semantic_ci + 本トラック（報告形式） |

決定論演奏者（`perform/`）を実行系に使うことでリンク 3・4 の不確実性をゼロに
固定し、リンク 1 を純粋にテストする。これが本トラックの中核の実験設計である。

### 1.2 意味そのものは検証対象外（恒久）

検証できるのは、LLM の意味設計が物理・構造軸に落とした**射影**（モチーフ回収・
密度曲線・谷・キー/BPM/構造の整合）の保存である。「聴き手が意味を感じるか」は
どの計器でも測れず、人間校正（WI3 型）の領分として本トラックから恒久に除外する。

## 2. 設計原則

### D1: アダプター = 決定論の国境。薄く・厳格に・全部 pin

アダプターは LLM 側の非決定論とエンジン側の決定論を隔てる税関である。賢さは
国境の両側（LLM の設計能力 / エンジンの計測能力）に置き、国境自体には置かない。
エンジンに自然言語解釈を入れない（LLM-free 決定論の原則を無傷に保つ）。
採択された Score は content hash で pin し、以降の演奏・計測・比較を再現可能にする。

### D2: アダプター = 情報の国境。エージェントの賢さによる汚染を防ぐ

LLM に見せてよいのは**契約**（スキーマ・著述ガイド・構造化報告）のみ。
エンジンのソースコード・validator 実装・config・生の抽出出力は見せない。
リポジトリ全読可のエージェントがループを回すと、成功が「言語が書ける」証明でなく
「エージェントが穴埋めできる」証明に化け、失敗の所在（言語仕様 / 報告形式 /
LLM 能力）が切り分け不能になる。M2e の direct/stem アーム分離と同じ動機。

この境界により、LLM 実装は差し替え可能（Claude / GPT / ローカルモデル）となり、
同一条件での比較が成立する。

### D3: Score 直書き。中間プランナーを挟まない

「LLM は高水準意図のみ書き、決定論プランナーが Score へ翻訳する」多段案は
採らない。翻訳層を挟むと失敗の所在が再び混濁する（設計が悪いのか翻訳が悪いのか）。
`CompositionScore` を LLM が直接書けるか自体が L0 の検証対象である。

### D4: intent sidecar の隔離

「なぜこの音があるか」（意味設計・モチーフ回収の意図）は Score と別ファイルの
intent sidecar に書かせ、**エンジンは一切消費しない**
（`learned_models_policy` の隔離原則と同型: 意図＝主張と計測＝evidence を混ぜない）。
intent は差分報告での設計意図 vs 実測の突き合わせ参照と、将来の人間校正の材料に
限って使う。

### D5: 帯域注釈を LLM まで運ぶ

差分報告の各数値に `measured / out_of_band / not_observed` を必須付与する。
これを怠ると LLM は信用できない数字に基づいて修正し、ループが発振する。
M0/M1 の観測ゲート規律を「LLM という消費者」まで延長する。

### D6: 報告は構造→構造。総合スコア禁止はここでも適用

差分報告は軸別・セクション別の構造化 evidence で返す（散文で返さない。
散文→修正の翻訳誤差が LLM 側に生まれる）。「全体 72 点」は修正指示に翻訳できないが
「B メロ: contour 保存 / rhythm 逸脱 / 谷が設計比 15% しか沈んでいない」は翻訳できる。
生データはファイルに置き、LLM には判断に足りる密度の要約とポインタを渡す。

### D7: 計器を被測定者に触らせない

LLM に config・閾値・帯域定義・凍結値の変更経路を与えない。校正を被測定者が
動かせる系は科学でなくなる。

## 3. 構成要素

```text
LLM（差し替え可能）
  │  入力: 著述契約（スキーマ + 著述ガイド）+ 前周の構造化差分報告
  │  出力: score.yaml + intent.yaml
  ▼
[1] 記号検証ゲート（音を出さない・秒オーダー）
  │  pydantic スキーマ検証 + ドメイン lint
  │  （小節連続性 / キーと和声の整合 / n_max / 音域の歌唱可能性 / 参照解決）
  │  エラーは機械可読の構造化リストで LLM へ返す（行き先粒度: セクション+フィールド）
  ▼
[2] pin（content hash: score_hash / intent_hash）→ 以降は決定論の世界
  ▼
[3] 実行と計測（既存部品、新規実装なし）
  │  perform（決定論演奏）→ extract → score-adherence / R0 比較 / （L0c で M3）
  ▼
[4] 差分報告生成
  │  軸別・セクション別 evidence + 帯域注釈 + intent 参照 + 生データポインタ
  ▼
LLM が Repair（semantic_ci の Diff → Repair の型に整合）→ [1] へ戻る
```

- 1 周 = `(score_hash, intent_hash, report_hash)` の三つ組を dated 記録。
- 周回上限を事前宣言（初期値 5 周）。収束しなければ「未収束」として正直に記録する
  （B_session と同じ思想: 超過は異常ではなく織り込まれた通常状態）。
- インターフェースはファイルベースの契約とする（sidecar-first の流儀に整合。
  `score.yaml` / `intent.yaml` in、`validation.json` / `report.json` out）。
  特定のエージェントハーネスや MCP に依存しない。

## 4. フェーズ

| フェーズ | 内容 | 依存 | 状態 |
|---|---|---|---|
| **L0-s** | 手動スパイク: エージェントが Score 直書き→検証→演奏→計測→修正を数周回し、契約に何が必要か（スキーマのどこで詰まるか / エラーメッセージの何が不足か / 報告に何があれば直せるか）を観測記録する | なし（既存部品のみ） | 未着手・次アクション |
| **L0a** | 著述契約の凍結: スキーマ公開範囲 + 記号検証ゲート + エラープロトコル。音声処理ゼロ | L0-s の観測 | 未着手 |
| **L0b** | 非旋律軸の閉ループ: 決定論演奏 + 既存センサー（BPM / キー / 構造 / 密度 / 谷）で差分報告 → Repair の 1 周を成立させる | L0a | 未着手 |
| **L0c** | 旋律軸の配線: モチーフ提示/回収の検収（M3 軸別 evidence 経由） | **M2e 破断曲線 + M4** | 凍結（依存待ち） |

L0-s / L0a / L0b は **M2e に依存しない**。M2e 本測定（15 シャード前後の消化試合）と
並走できるが、実行リソースは M2e 優先とする（同一 VM で回す場合、スパイクの
演奏・抽出は本測定の隙間で行う）。

### 4.1 L0-s スパイク計画（最小設計）

- **課題**: 小規模の意味設計課題を 1 つ事前登録する（例:「静→動の 3 セクション、
  B で密度を単調増加させ、C 直前に谷を作る」）。旋律の指定は含めない（L0c 凍結中）。
- **手順**: エージェントが著述契約の範囲内の情報のみで Score を書く → 既存 CLI で
  演奏・抽出・比較 → 差分を読んで修正、を最大 5 周。
- **記録**（スパイクの主生産物。曲の出来ではない）:
  1. スキーマ理解の失敗点（どのフィールドで誤解が起きたか）
  2. 検証エラーの表現不足（何を言われれば直せたか）
  3. 差分報告に必要だった情報（何が無くて生データを見に行ったか）
  4. 周回ごとの三つ組 `(score_hash, intent_hash, report_hash)` と収束の推移
- **注意**: スパイク実施エージェントはエンジン実装を読まずに回すこと（D2 の
  手動遵守）。読まざるを得なかった箇所こそが契約の欠陥であり、最重要の記録対象。

## 5. 成功条件・停止条件

- **L0-s の成功**: 契約仕様の草案が書ける程度の観測が collected（周回の成否は問わない）。
- **L0b の成功**: 事前登録した設計課題に対し、非旋律軸の差分が周回で単調に減少する
  ケースが 1 つ以上実測される（= 閉ループが操舵として機能する証拠）。
- **停止条件**: 5 周で記号検証ゲートを一度も通過できない場合、Score 直書き（D3）を
  見直す設計判断へ差し戻す（中間表現の再検討はこのときのみ開く）。

## 6. 未解決課題

- 著述契約に含めるスキーマ文書の粒度（pydantic モデルの自動書き出しか、手書きガイドか）
  — L0-s の観測で決める。
- 差分報告のスキーマ（`report.json`）の正規形 — L0-s の観測で決める。
- 生成器（Suno / MusicGen）への接続はリンク 3（K 系列）の宿題であり、本トラックでは
  決定論演奏者の先に進まない。grip が小さいと出た場合「LLM の設計は正しいのに
  生成器が従わない」ことが数値で示せる状態を成果とする。
- LLM 間比較（D2 の差し替え可能性の実証）は L0b 成立後の拡張とする。
