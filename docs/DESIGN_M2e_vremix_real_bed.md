## 1. 方法（1段落）

vocadito の歌声 clip（正解 f0 注釈つき・CC BY 4.0・M2c で取得済み・sha256 pin 済み）に
MUSDB18-HQ の器楽ベッドを決定論ミックスして疑似フルミックスを作り、2 経路
（分離なし / demucs vocals stem 経由）で crepe 抽出し、vocadito 注釈と mir_eval 照合する。
**加算ミックスは歌声の f0 を変えないため、正解注釈はそのまま有効。**
測っているのは「主旋律の支配度が下がったとき音高追跡がどこで壊れるか」であり、
実運用（Suno テイク → 比較）で melody anchor を信用してよい範囲の直接検証である。

## 3. 素材

### 3.1 歌声（正解側）

vocadito **40 clip**。`m2c_external_fixtures.yaml`（`m2c-external-fixtures/0.1`・
`registered_utc: 2026-07-29`）の既存 pin をそのまま使用。**再取得・再エンコード禁止。**

### 3.2 ベッド（伴奏側）

**MUSDB18-HQ の `drums + bass + other` を生サンプル加算したもの。**

`vocals.wav` は**使わない**（読み込みもしない。存在確認のみ）。使えば vocadito の声と
二重になり、正解注釈がどちらの声を指すのか定義できなくなる。MUSDB18-HQ の stem は
mixture へ厳密に加算合成されるので、`drums+bass+other` は当該曲の器楽のみのトラックに
正確に一致する。

**なぜ合成ベッドより上位か:** `S_fullstack: {}`（バーなし）の根拠は「Demucs は合成音色に
対し分布外」だった。ベッドが実プロ制作音源になると**この除外理由が効かなくなる**。
これが §5.4 で stem アームを診断専用から引き上げられる唯一の根拠である。

### 3.3 ベッド選定 — 事前登録された決定論的手続き

**本書ではトラック名を列挙しない。** 未検証のまま曲名を書けば、それは pin ではなく捏造。
選定規則のみを凍結し、結果を M2e-r1 で pin する。

1. MUSDB18-HQ 配布物のトラック一覧を取得し、**`test` split を lexical order** に並べる
   （並べ方をスクリプトに凍結・実装者の裁量を残さない）。
2. **全 50 曲**に §3.4 のスクリーニングを実施し、全件の実数値を記録する。
3. 採用は **lexical order 先頭から、通過した 2 件で停止**。
4. **全 50 の分布は記録であって選定入力ではない。** 通過2件の確定後に、より下位の
   通過曲へ差し替えることは禁止。密度・ジャンル・漏れの小ささ等の性質で選ぶことも禁止。
   **順序のみで決める。**

「1件目を密なベッド、2件目を疎なベッド」と呼び分けない。密度で選ぶと選定が結果に
依存しうる。

#### 3.3.1 `lexical order` の定義（凍結）

本書で `lexical order` と書いたものは、**UTF-8 バイト列の辞書式順序**と定義する。

- **既取得順序は引き直さない。** UTF-8 は「バイト列辞書順 ＝ コードポイント順」が
  恒等に成り立つ符号化である。実行側が凍結値として採用している codepoint 順は本定義と
  同一物であり、再導出は不要。ここで決めているのは**新しい順序ではなく、既にある順序の
  名前と、それ以外の順序の禁止**である。
- **禁止:** ロケール依存照合（`LC_COLLATE` / ICU / `locale.strxfrm` / shell `sort` の既定
  挙動）。shell で並べる箇所があれば `LC_ALL=C` を明示する。Python の `sorted()` は `str`
  に対しコードポイント順なので、追加指定なしで条件を満たす。
- **Unicode 正規化を一切適用しない。** NFC/NFD 変換はバイト列を変え、したがって順序を
  変えうる。id は記録されたまま比較する。
- **比較対象は「ファイルシステム列挙結果」ではなく「pin された id 文字列」。**
  M2e-r1 で 50 件の id を `m2e_bed_fixtures.yaml` に pin した後は、順序は pin されたバイト列
  だけから再現でき、OS・展開系・ファイル名正規化の差は入らない。pin 前の1回の列挙に
  ついては、第三者は**集合一致（順序非依存）**で配布物との同一性を検証できる。
- **比較キーはタプルであり、連結文字列ではない。** 区切り文字がフィールド値に現れた
  瞬間に連結キーは順序を壊す。

**§8.5 のセル整列キーへの適用（自由変数を消す）:**

- `level` は**文字列としては並べない**。ラダー宣言順の添字 `ladder_index`
  （`+12dB`→0, `+6dB`→1, `0dB`→2, `−6dB`→3）で並べる。`"+12dB" / "+6dB" / "0dB" / "-6dB"`
  をバイト辞書順に並べると `+12dB, +6dB, -6dB, 0dB` となり、物理量と無関係な順序になる。
  ラダー順に並べれば、途中で終わった実行についても「易しい側から埋まっている」と
  説明できる。
- `repeat_idx` は**整数として比較**する（文字列化しない）。
- `bed_id` / `clip_id` / `arm` は本節の定義で比較する。

この確定はシャード地図（スケジューリング）にのみ影響し、セル台帳には影響しない。
かつ本測定は 1 セルも走っていないので、**いま確定させるのは無償**である。r2-0 以降に
同じ確定を行えば、それは実行中の順序変更になる。

### 3.4 スクリーニング — 20 dB 不変量

#### 3.4.1 不変量（上位規定）

> **ベッドの残留ボーカルは、宣言した全水準において vocadito の歌声より 20 dB 以上
> 下にあること。**

20 dB は「寄与を無視できる」の標準余裕（振幅 1/10・電力 1/100）。**この値は動かさない。**

#### 3.4.2 指標と閾値

**指標:**

```
residual_db = 20 * log10( RMS(demucs vocals stem of bed) / RMS(bed) )
```

RMS の定義は §4.3。**両者を同一フレーム集合で評価する。**

**閾値:** `residual_db <= hardest_level_db - 20.0`。現ラダーの最難水準は −6 dB なので
**`residual_db <= -26.0` を採用条件**とする。−26 は §3.4.1 の不変量を現ラダーで評価した
値にすぎず、独立した自由パラメータではない。

#### 3.4.3 フィッティングでないことの監査可能性

本設計の起草時点で設計側が受け取っていたのは「3素材が**約 33 dB 差**で分離した」という
**差**のみで、**絶対値は知らされていない**。よって −26 dB を観測値へ合わせることは
物理的に不可能である。この非依存性を検証可能にするため:

- 実行側は当該3素材の `residual_db` **絶対値**を記録する。
- **−26 dB が観測 gap の内側に落ちたか外側かを報告**する。
- **外側だった場合でも閾値は動かさない。** それは所見であって救済理由ではない。

#### 3.4.4 未検証点の扱い

- **器楽漏れ床の変動**は過剰棄却の方向にしか効かない（漏れが大きい曲が落ちるだけ）。
  選定は lexical order 先頭から通過2件なので、過剰棄却はリストを下へ進むコストにしか
  ならない。**fail-closed で安全側。** §3.3-2 の全件測定でこの変動自体が実測される。
- **中間帯（小さいバックボーカル）**は −26 dB より上なら落ち、下なら定義上寄与が
  無視できる量なので、境界でも原理が通る。

#### 3.4.5 目視の位置づけ

スペクトログラムは**記録として必ず残す**が、判定入力としては**棄却方向にのみ効く
一方向オーバーライド**とする。目視で持続的な歌唱が明らかなら数値が通っても不採用。
逆（数値が落ちたものを目視で救う）は禁止。

**期限（是正）: 生成と判定は M2e-r2 の内側で閉じる。** 従来「r3 までに」と読める書き方を
していたが、これは緩すぎる。一方向オーバーライドが清潔でいられるのは「音高の結果を
まだ見ていない」という一点に依存している。本測定が 1 セルでも走った後の棄却は、
**結果を見て素材を落とす操作と外形が区別できない**。よって r2 を出るまでに閉じ、
r3（ベッド pin・バー登録）へ持ち越さない。

**棄却事由は、画像を見る前に書いて日付を打つ。** さもなくば「気に入るまで見る」という
裁量になる。事前登録する棄却事由は以下で**確定**とし、画像を見た後の追加を禁止する:

- **(a)** vocadito 声の F0 帯に、持続する調波列・声道フォルマント構造が可視
- **(b)** リード歌唱の残留が可視（コーラス・ハミング・ダブリングを含む）
- **(c)** クリッピング（全帯域にわたる飽和縞）
- **(d)** 測定窓 `[0, n_max]` 内に連続 1.0 秒以上の無音・欠落（**数値定義は §3.4.6。
  目視事由ではなくスクリプト判定へ移す**）
- **(e)** 16 kHz 付近の帯域打ち切り（"HQ" が非可逆再圧縮由来である徴候）

判定は bed ごとに「該当事由（a〜e のいずれか）／なし」を **1 行で dated 記録**する。

**採用済み 2 件を倒すことについて:** 規定上可能である。ただし r2 の内側で、かつ (a)〜(e)
のいずれかを明示した場合に限る。倒したら **§3.3 の pin された順序の次の通過曲へ進む**
（手選び禁止・順位を飛ばして選び直すことも禁止）。順序を進めるのは r3 でベッドを確定
させる前なので、r3 以降の再改訂は発生しない。

**追加の禁止:** 画像を見てから `residual_db` の閾値・20 dB 不変量・測定窓 `n_max` を
動かすこと。目視は素材を落とせるが、**規準は一切動かせない**。

**画像の保管:** スペクトログラム画像は**リポジトリへ commit しない**。理由は3点 —
波形非コミット規律の趣旨、MUSDB18-HQ が非商用研究ライセンスであり市販録音の派生図の
再配布は避けるべきこと、高分解能の線形振幅スペクトログラムが近似復元を許すこと。
**commit するのは生成スクリプト・各画像の `sha256`・1 行判定**であり、画像本体は
リポジトリ外に保管して成果物として提出する。生成条件（窓長・hop・周波数軸・dB レンジ・
カラーマップ）はスクリプトに凍結し、実行者の裁量を残さない。

#### 3.4.6 棄却事由 (d) の数値定義 — 導出（新規自由パラメータ 0 個）

(d) を「連続 1.0 秒以上」とだけ書いて**無音の定義を書かなかった**のは欠陥である。
実行側から3案（厳密ゼロ / −60 dBFS_peak / −80 dBFS_peak）の提示を受けたが、
**3案とも採らない。** 理由と、代わりに採る定義を書く。

**まず (d) が何のための事由かを確定する。** (d) は音質の良し悪しではなく、
**宣言した水準が局所的に成立していない**ことを捕まえるためにある。ベッドが局所的に
落ちれば、そこでは声/ベッド比が宣言値より上がり、セルが主張している「声はベッドより
6 dB 下」が実際には成り立たない。つまり (d) の判定基準は「静かか」ではなく
**「ベッドが宣言上無視できる量まで落ちているか」**である。

これは既に §3.4.1 で凍結してある量そのものなので、導出できる。

```
基準量 : bed_active_rms  = §4.3 の非無音フレーム RMS（2048 / 512・−40 dB 判定）
          （[0, n_max] のベッド波形 = drums+bass+other の和・タイル連結後）
frame_db(t) = 20 * log10( RMS_frame(t) / bed_active_rms )

dropout フレーム ⟺ frame_db(t) <= -26.0
     -26.0 = -( |hardest_level_db| + level_margin_db ) = -( 6.0 + 20.0 )

(d) 該当 ⟺ dropout フレームが N_drop = ceil(sr / hop) = ceil(44100 / 512) = 87 フレーム
           以上連続する区間が [0, n_max] 内に存在する
```

**導出の中身:** 最難水準では声 = ベッド − 6 dB。ベッドが自身の active RMS から 26 dB
落ちれば、その区間でベッドは声より 20 dB 下 — §3.4.1 の不変量が「無視できる」と
定義した量である。**§3.4.2 の `residual_db <= -26.0` と同じ定数・同じ基準量
（bed RMS）**であり、分子が残留ボーカルかベッド自身かが違うだけ。
「ベッド基準 −26 dB より下は宣言水準では無視できる」という**一つの規準**が両軸に
効いている。新しい自由パラメータは 1 個も入らない。

**3案を採らない理由:**

- **厳密ゼロ** — デジタルな穴しか捕まらない。ディザやノイズフロアが乗ったフェード
  アウト・実質的な空白は素通りする。本設計は全域が水準相対で書かれており、
  絶対ゼロという基準はどこにも宣言されていない。
- **−60 / −80 dBFS_peak** — **peak は本設計のどこにも宣言されていない基準量**であり、
  かつ**たった 1 サンプルで決まる**。スネア 1 発の有無で判定が 6 dB 動く量を
  棄却基準の分母に置くべきではない。§4.3 が RMS を非無音フレームで定義しているのは
  まさにこの理由による。

**ここで最も重要な点（自己申告）:** 私は 3 案それぞれがどのトラックを落とすかを
**見た後で**この裁定を書いている。だから「見なかったことにする」のではなく、
**結果の分からない定義を導出で立てる**ことで手を縛る。§3.4.6 の判定結果は現時点で
未知であり、**出た結果がどれであっても受け入れる** — track 0 のみ棄却、track 1 のみ棄却、
両方棄却、両方存続、いずれも同じ扱いとする。

- **1 回きり。** §3.4.6 を適用した結果が気に入らないことを理由に、別の定義を試すこと、
  −26.0 を動かすこと、`N_drop` を動かすことを**禁止**する。
- **窓は動かさない。** 冒頭に穴があっても `[0, n_max]` を後ろへずらして回避することは
  §3.5 の「良い区間を探す」禁止に該当する。**逃げ道は棄却だけ**である。
- 棄却されたら §3.3 の pin 順序の次の通過曲へ繰り上げる。**両方棄却でもコストは
  リストを下へ進むことだけ**で、科学的な損失はない（§3.4.4 と同じ構造）。
- `dropout_max_seconds` を **全 50 曲について記録**する（§3.3-2 と同じ趣旨。採用候補
  だけ測ると、閾値が分布のどこにあるかを後から検証できない）。

**副次的だが決定的な理由:** ダイナミクスに反応する厳しい閾値（例えば「+12 dB 水準で
壊れる = −8 dB」）を採ると、通常の音楽的な休符で片端から落ち、**圧縮された密なトラック
だけが生き残る**。それは §3.3-4 が明示的に禁じた「密度でベッドを選ぶ」ことと同じ結果を
裏口から達成してしまう。−26 dB は**楽曲のダイナミクスではなく素材の穴**を切る位置に
あり、この裏口を開けない。

#### 3.4.7 §3.4.6 の読み違えを塞ぐ明確化（2026-08-01・rev.5／内容変更なし）

M2e-r2 の実装が (d) の判定閾値に **−40 dB** を採った。これは誤りである。以下は
rev.3 §3.4.6 の**再言であって改訂ではない**（数値・規則は一字も変えていない）。

**2 つの数は役割が違う。**

| 数 | 出典 | 役割 |
|---|---|---|
| **−40 dB** | §4.3 | **基準量を作るためのゲート**。`bed_active_rms` を算出する際に、どのフレームを active とみなすかの判定。判定閾値ではない |
| **−26.0 dB** | §3.4.6 | **(d) の判定閾値**。`frame_db(t) <= -26.0` を満たすフレームが dropout |

§3.4.6 が「§4.3 の非無音フレーム RMS（2048 / 512・−40 dB 判定）」と書いているのは
**基準量 `bed_active_rms` の定義を参照している**のであって、判定閾値を −40 dB に
するという意味ではない。**(d) の判定閾値は −26.0 dB のみ**である。

**監査はフレーム単位で行う（秒は従属表示）。** `dropout_max_seconds` の実体は
`ceil` された整数フレーム数であり、分解能は `hop / sr = 512 / 44100 = 11.610 ms`。
量子化された量を連続量の「余裕」で語ると意味を取り違える。§3.4.3 形式の監査で
報告する量を固定する:

```
(i)   非該当の最大フレーム数  n_pass_max
(ii)  該当の最小フレーム数    n_fail_min
(iii) gap = n_fail_min - n_pass_max              [フレーム]
(iv)  閾値余裕（非該当側）    = N_drop - n_pass_max   [フレーム]
(v)   n_fail_min == N_drop か（真なら「閾値上に該当が載っている」）
```

**(v) が真になることは異常ではない。** 判定が `>= N_drop` の整数閾値である以上、
最小限に該当したトラックが 1 件でもあれば **構造的に必ず** `n_fail_min == N_drop` に
なる。これを「余裕 0.000 秒」と書くと、連続量である `residual_db` の 0.270 dB と
同種の脆さに見えてしまうが、別物である。**閾値の頑健さを表す量は (iv)** である。

ただし (v) が真のとき、**そのトラックは 1 フレーム（11.610 ms）の摂動で該当↔非該当が
反転しうる**。これは実在する脆さなので、
**「どのトラックが」「反転した場合に採用へ効くか」を明記して記録する**。pin 順序で
採用 2 件より下にあり、かつ繰り上がりがそこへ到達していないなら **decision-inert** で
あり、その条件つきである旨を書く（§3.4.5 の未目視 44 件と同じ扱い）。

**閾値は動かさない。** (v) が真であることを理由に `N_drop` や `-26.0` を動かすことは
§3.4.6 の「1 回きり」条項および §13 で既に禁じてある。監査は**開示の器具であって
ゲートではない**。

### 3.5 測定窓

ミックスは常に曲頭 0.0s 起点なので、**使う範囲だけを screen する**のが正しい。
曲の後半にボーカルがあってもミックスに入らないなら不問。

- **`n_max`** = 事前登録された vocadito **40 clip の最長サンプル数**。
- **スクリーニング窓 = ベッドの `[0, n_max]`**（短ければ §4.2 のタイル連結で延長）。
- `n_max` は**常に 40 clip 基準で固定**する。窓が実行規模に依存すると、素材の合否が
  計算資源で変わってしまう。
- `n_max` の実数値（サンプル数・秒）を `m2e_bed_fixtures.yaml` へ pin する。

**参考（設計側の推定・要確認）:** 実行報告の「約81%がミックスに入らない」を180秒基準で
逆算すると使用域は約19% ＝ **34秒前後**。実測で確定すること。

### 3.6 水準ラダー（事前登録・4点）

歌声/ベッドの **RMS 比 +12 / +6 / 0 / −6 dB**。RMS は非無音フレームのみで算出（§4.3）。

#### 3.6.1 ラダー端の事前登録された縮退規則

全50曲で通過が2件に満たない場合、**動かすのは閾値ではなくラダーの難しい側の端**。

```
hardest_level_db = residual_db_of_selected_beds + 20.0
```

- 残留が −20 dB の素材しか無ければ最難水準は **0 dB** までとなり、**−6 dB の点を失う**。
- 余裕 20 dB は絶対に動かさない。
- これは「バーを緩める」ではなく「**この素材で届く射程はここまで**」の宣言であり、
  破断曲線の到達範囲が縮むという形でレポートに必ず現れる。
- **易しい側へ切り詰めることはあっても、素材に合わせて広げることはしない**
  （+12 dB より上を足して救済することは禁止）。
- 縮退したら、縮退後のラダーと `residual_db` の実数値を帯域地図に併記する。
- **全50曲で通過0件の場合、本帯は登録しない。** MUSDB18-HQ が要求余裕を満たすベッドを
  供給できない事実を dated 記録し、素材問題を §12 の User 決裁へ差し戻す。

## 4. 決定論ミックス生成仕様（`scripts/make_vremix_fixtures.py`・自由変数ゼロ）

seed 不使用・完全決定論。**波形は commit しない**（pin のみ）。
本節と既存実装が食い違う場合は §4.7 に従う。

### 4.1 入力と前処理

```
sr_clip, voice = read(vocadito clip)                    # mono, float64
sr_bed,  stems = read(drums.wav, bass.wav, other.wav)   # 44.1kHz stereo, float64

if sr_bed != sr_clip: raise                             # 暗黙のリサンプルは禁止（停止する）
bed_st   = stems.drums + stems.bass + stems.other       # サンプル単位の生加算
bed_mono = 0.5 * (bed_st[:, 0] + bed_st[:, 1])
```

| 項目 | 規則 | 理由 |
|---|---|---|
| チャンネル | ベッドを `0.5 * (L + R)` でモノ化 | vocadito はモノ。ステレオのまま混ぜると水準定義が曖昧になる |
| サンプルレート | **リサンプルしない。** 不一致は**例外で停止** | 暗黙のリサンプルは pin できない変換を混ぜる |
| 区間 | 各ベッド曲の **先頭 0.0s から**必要長を取る | 「良い区間を探す」余地を残さない |

### 4.2 長さ合わせ（タイル連結・10ms 線形クロスフェード）

```
xf = int(round(0.010 * sr))                   # 44100Hz → 441 samples
if len(s) <= xf: raise                        # ソースが短すぎる
w  = arange(xf, dtype=float64) / xf           # [0, 1/xf, ..., (xf-1)/xf]（右端を含まない）

out = s.copy()
while len(out) < n_target:
    head = out[-xf:] * (1.0 - w) + s[:xf] * w
    out  = concatenate([out[:-xf], head, s[xf:]])
seg = out[:n_target]
```

`n_target` はスクリーニングでは `n_max`（§3.5）、ミックス生成では当該 clip のサンプル数。
**区間は常に曲頭 0.0s 起点。**

### 4.3 RMS（非無音フレーム）

```
frame_len = 2048
hop       = 512
# 中央寄せ（centering）なし。フレーム k は [k*hop, k*hop+frame_len)。
# 末尾の埋まらないフレームは破棄。
frame_rms[k] = sqrt(mean(x[k*hop : k*hop+frame_len] ** 2))
active       = { k : frame_rms[k] >= max(frame_rms) * 10 ** (-40/20) }   # ピークから-40dB
if active is empty: raise
RMS(x) = sqrt( mean over k in active of frame_rms[k] ** 2 )
```

**§3.4.2 の `residual_db` では、vocals stem の RMS も `bed` 側で選ばれた `active` を
そのまま用いる**（stem 自身で active を選び直すと、器楽曲の漏れが自己正規化で持ち上がり、
退役した旧指標と同じ罠に落ちる）。

### 4.4 水準適用

```
V = RMS(voice_seg); B = RMS(bed_seg)
g_v = 1.0                                     # 歌声は無加工（正解側を触らない）
g_b = (V / B) * 10 ** (-R_db / 20.0)          # R_db ∈ {+12, +6, 0, -6}
mix = voice_seg * g_v + bed_seg * g_b
```

検算: `(V*g_v) / (B*g_b) = 10 ** (R_db/20)`。

### 4.5 クリップ回避（リミッタ・正規化は禁止）

```
peak     = max(abs(mix))
headroom = 0.98 / peak
factor   = min(1.0, headroom)                 # 両成分に共通 → RMS 比は厳密に不変
mix_final = mix * factor
```

リミッタ・ラウドネス正規化・水準ごとの個別正規化はいずれも歌声/ベッドの比を変え、
**宣言した SNR を破壊する**ので禁止。`factor` を **(clip_id, bed_id, level) ごとに
manifest へ記録**。1.0 未満になった組み合わせの偏りは検収時の確認項目。

### 4.6 出力と pin

```
waveform_sha256 = sha256( mix_final.astype(float32).tobytes() )
```

既存 `m2_accuracy_bars.yaml` の `waveform_sha256` 規約（float32 tobytes）と同一。
**波形は commit しない。** dither なし・resample なし・normalize なし・limiter なし。

### 4.7 demucs へのチャンネル受け渡し（既存実装が優先）

モノ信号を demucs へ渡す際の複製規約と、出力 stem のモノ化規約は、**既存の
`demucs_vocals_then_crepe` 経路の実装をそのまま流用する**。新しい規約を発明しない。
既存実装が本節の想定と異なる場合は**既存が勝ち、本書を訂正する**（規約が2つに割れる
ことのほうが有害）。流用した実装の該当箇所を記録に明示すること。

### 4.8 CI（音源不要の単体テストのみ）

決定論（同一入力 → bit 一致）／`n_target` 展開／クロスフェード境界（`len(s) == xf+1` 等の端）
／`factor` 算出／**rate 不一致で例外送出すること**／**`vocals.wav` を読まないこと**。

## 5. 帯・バー・条件（実測前に凍結）

### 5.1 事前登録ファイルの分離

M2e の帯は **`tests/fixtures/melody_bench/m2e_accuracy_bars.yaml`（新規）** に置く。
`m2_accuracy_bars.yaml` へは追記しない。

理由: `bars_sha256` は「この帯の判定がどのバーの下で出されたか」を固定する pin であり、
M2e の帯を追記して M2b / M2c の commit 済み verdict の pin が壊れるのは、その機構の
**偽陽性**である（M2b / M2c が使ったバーの中身は1バイトも変わらない）。
pin を帯単位 digest に変える案は既存の全 pin を無効化する code change であり、
**避けたい事態（dated 再実測）を自ら引き起こす**。リポジトリは同じ理由で既に2回
この分離をしている（`registry.yaml` → `m2_accuracy_bars.yaml` → `m2c_external_fixtures.yaml`）。
3例目として同じ流儀に従う。**M2b / M2c の再実測は行わない。**

分離の条件:

1. **一方向規律の明示的継承。** 新ファイル冒頭に、`m2_accuracy_bars.yaml` と同じ
   「registered_utc つき・実測前凍結・実測後に緩めない」規律が適用されることと、
   分離の理由を書く。**暗黙の継承にしない。**
2. **`schema_version` を分ける:** `"m2e-accuracy-bars/0.1"`。M2 の
   `"m2-accuracy-bars/0.1"` を名乗らせない。
3. **転用値の出所を記録する。** `min_rpa: 0.65` / `max_octave_gap: 0.10` は
   `m2_accuracy_bars.yaml` の `V_fullstack` からの転用。ファイルを跨いだ時点で出所が
   追えなくなるので、provenance に
   `derived_from: {file: m2_accuracy_bars.yaml, sha256: <転用時点の値>, category: V_fullstack}`
   を記録する。
4. **共有スカラーは再宣言せず参照する。** `tolerance_cents` /
   `est_voiced_confidence_floor` / `repeats_min` は M2 側の値を使う。参照が実装上難しい
   場合は同値を書いた上で、**M2 側との一致を検証するテストを置く**（二重定義は必ず
   食い違う）。
5. **同一カテゴリ名が2ファイルに現れたら fail-closed**（§5.2）。
6. **これは「pin が壊れたらファイルを分ける」の一般許可ではない。** 本件が正当なのは
   **M2e の実測が 0 件**だからである。**実測値を見た後に、落ちた pin を回避する目的で
   ファイルを分けることは禁止。** `registered_utc` と「この時点で M2e の実測記録は 0 件」
   の事実を明記すること。

### 5.2 カテゴリ所有権と検証スコープ（分離が要求する新規定）

`run_melody_accuracy.py` の bars 検証は `for category in sorted(_CATEGORY_SPECS)` を回して
「バーが空なら fail-closed」とするので、**`_CATEGORY_SPECS` に M2e カテゴリを足した瞬間、
`m2_accuracy_bars.yaml` の検証が「M2e のバーが空だ」と誤爆する。**

- 各カテゴリは **ちょうど1つの bars ファイルに所有される**。所有権は `_CATEGORY_SPECS`
  の各行に `bars_file` を持たせて表現する。
- 検証は**所有カテゴリのみ**を対象に行う。他ファイルのカテゴリの不在を欠落と見なさない。
- **fail-closed 条件（緩めてはならない）:**
  - 所有ファイルが未指定のカテゴリがあれば拒否（「どこにも属さない」カテゴリは検証を
    素通りする。分離が開ける唯一の穴なのでここで塞ぐ）。
  - 2ファイルに同名カテゴリが現れたら拒否。
  - bars ファイルに、そのファイルが所有しないカテゴリの block があれば拒否。
- 精度 run の provenance には、**使った bars ファイルの相対パスと sha256 の両方**を
  記録する。

**`V_fullstack` の扱い（現状の事実確認）:** `V_fullstack` は `m2_accuracy_bars.yaml` に
バーを持つが `_CATEGORY_SPECS` に行が無い。つまり「事前登録済み・未配線」の帯が既に
存在する。**帯の登録はハーネス配線を前提にしない**という先例である。
**`V_fullstack` を本件のついでに配線してはならない**（別件・別 PR）。

### 5.3 バー block と条件 block

`m2e_accuracy_bars.yaml` に**2つの兄弟 block**を置く。条件 block を bars block の中へ
入れると loader が dict 値をカテゴリと誤認するので、**必ず兄弟にする。**

```yaml
m2e_accuracy_bars:
  V_remix_real_direct:
    min_rpa: 0.65               # 新値を発明せず V_fullstack 凍結値を転用。
    max_octave_gap: 0.10        # 意味は「昇格要件」ではなく「反証床」
  V_remix_real_stem:
    min_rpa: 0.65
    max_octave_gap: 0.10

m2e_measurement_conditions:
  level_margin_db: 20.0                              # §3.4.1 の不変量。実験全体で1つ
  V_remix_real_direct:
    gate_level: "+12dB"
    levels: ["+12dB", "+6dB", "0dB", "-6dB"]
  V_remix_real_stem:
    gate_level: "+12dB"
    levels: ["+12dB", "+6dB", "0dB", "-6dB"]
```

- `_REQUIRED_BAR_KEYS_BY_CATEGORY`: 両カテゴリとも **`("min_rpa", "max_octave_gap")`**。
- 新設 `_REQUIRED_CONDITION_KEYS_BY_CATEGORY`: 両カテゴリとも **`("gate_level", "levels")`**。
  **バーを持つカテゴリが条件 block を欠いたら fail-closed。**
- 追加の fail-closed: `gate_level ∈ levels` でなければ拒否。`levels` が §3.6 の4水準と
  完全一致（順序込み）でなければ拒否。
- **`_DIAGNOSTIC_ONLY_CATEGORIES` は変更しない**（`{"S_fullstack"}` のまま。§5.4）。
- **`gate_level` / `levels` をバー block に入れてはならない。** これらは judge が数値比較
  する閾値ではなく「何を測ったか」の宣言であり、`_BAR_THRESHOLD_RANGES`（有限数値・
  値域つき）を通せない。通すために検査を緩めることは禁止（附録A-4）。
- **VFA / VR はバー外・診断記録のみ。** M2d が voicing 非信頼を確定済みで、下流の
  M3 / M4 は抽出器 voicing を消費しない（M3 は共有有声整列のみ・M4 は axis_evidence のみ）。
  消費されない軸で帯全体を fail させると S_direct の再演になる。

`level_margin_db` は**実験全体で唯一の宣言**とし、`m2e_bed_fixtures.yaml` の
`residual_db <= -26.0` は**導出値**として導出元を併記する。2箇所で独立に書き換えられる
状態にしない。

### 5.4 バーの意味論（取り違えると設計が壊れる）

- **両アームとも非昇格帯である。** 通過しても `demucs_vocals_then_crepe` は calibrated へ
  昇格せず、**M4 の G2 も解錠しない**（§7.2）。
- **`gate_level: "+12dB"` に限ってバーを当てる理由:** +12dB は事実上 `clear_lead` 相当。
  ここで `min_rpa 0.65` すら割るなら、通過済みの `V_direct`（実声・分離なし・
  `min_rpa 0.80`）と整合しない。**帯の合否ゲートではなく V_direct との整合トリップワイヤ**
  である。割れたら crepe を責める前に、ミックス式・水準算出・注釈整列・モノ化を疑う。
- **stem アームで +12dB を選ぶ意味:** 声がベッドより 12dB 大きいミックスは分離が最も
  易しい条件。ここを割るなら分離器の投入手順そのものが壊れている。
- **それ以外の水準（+6/0/−6dB）はバーを持たない。** 主生産物は合否ではない（§7）。
- **stem アームの引き上げ:** ベッドが実プロ音源になった以上、「Demucs は合成音色に対し
  分布外」という `{}`（バーなし）の根拠は成立しない。よって `V_remix_real_stem` は
  `_DIAGNOSTIC_ONLY_CATEGORIES` に**入れない**。これは**締める方向の変更**であり、
  一方向規律に反しない（規律が禁じるのは緩和のみ）。
- **単調性の扱い:** direct アームでは「SNR が高いほど易しい」が素材によらず成立する。
  stem アームでは分布外の懸念は外れたが、**Demucs が水準軸に沿って厳密に単調である保証は
  ない**（現実のミックスは声が伴奏より 12dB 大きくないため、+12dB 側が Demucs にとって
  典型的とは限らない）。よって stem アームでは**「+12dB で割れたら下の水準も割れる」と
  いう下方伝播を主張しない。** バーは +12dB 単点のトリップワイヤとしてのみ機能する。

### 5.5 命名規律

帯名に **`real` を含めることは必須**。集計表を読んだだけでベッドが実音源であると分かる
必要がある。`V_remix` / `V_fullstack` と接尾辞を共有する名前は将来の横断集計で静かに
混ざるため禁止。

## 6. ハーネス配線

### 6.1 `_CATEGORY_SPECS`

```python
"V_remix_real_direct": {
    "kind": "external",
    "input_kind": "full_mix_direct_probe",     # §6.3 で新設（追加のみ）
    "route_name": "crepe_direct",
    "bars_file": "m2e_accuracy_bars.yaml",     # §5.2
},
"V_remix_real_stem": {
    "kind": "external",
    "input_kind": "full_mix",                  # 既存のまま
    "route_name": "demucs_vocals_then_crepe",
    "bars_file": "m2e_accuracy_bars.yaml",
},
```

`kind: "external"` なので `fixture_id` / `composite_id` は**持たない**（`V_direct` と同じ）。

**なぜ `external` か（`fullstack` ではない）:** `kind: "fullstack"` は
`specs["composites"]` からハーネスが合成波形を組む経路で、合成 fixture 専用である。
M2e の入力は、実声（vocadito・外部素材・外部注釈）と実伴奏（MUSDB18-HQ stem・外部素材）を
オフラインの `scripts/make_vremix_fixtures.py`（§4）が混ぜた**実ファイル**であり、正解は
ミックスで変化しない vocadito の注釈である。これは `kind: "external"` の定義そのもの。
ハーネスに新しい合成経路を足さず、音声波形はリポジトリに入らない
（manifest がリポジトリ外を指し、`_external_manifest_protected_paths` の preflight も
そのまま効く）。

### 6.2 manifest の粒度・id 規約・水準の扱い

- **manifest は水準ごとに1本**生成する。1本には `40 clip × 2 bed = 80` 件。4水準で4本。
- **アームは manifest を分けない。** 同じミックスを2経路で測るのがアーム比較の定義であり、
  同一ファイルを共有することで素材差の混入が構成上不可能になる。
- entry id 規約: **`vremix_{clip_id}_{bed_id}_{level_tag}`**、
  `level_tag ∈ {p12, p06, p00, m06}`。
- 総抽出回数の一致確認: `80 mix × 4 水準 × 2 アーム × n=2 = 1280`。§8.1 のセル台帳と
  一致する。**一致しない実装は誤り。**
- **`level` はカテゴリではなく run の次元。** `_CATEGORY_SPECS` に持ち込まない。
  run report の各 row と cat_result に `level` を記録する（`external_manifest_sha256` と並べて）。
- **判定規律（fail-closed）: `level != gate_level` の run にバーを適用しない。**
  適用しようとしたら拒否する。`gate_level` 以外の水準は**破断曲線の記録専用**であり
  合否を出さない（§5.4 の「単点トリップワイヤ」の実装上の意味はこれ）。
- 帯の判定は `gate_level` の run が §11 のセル census を満たしたときにのみ出る。
- **実装ノート（2026-08-01・Codex 18 巡目 P1）**: `evaluate_m2_bars` は M2e カテゴリに
  対して `pass` / `fail` を**出さない**。`gate_level` ではバーを当てて
  `bar_satisfied` と `failures` に証拠を残し、`status` は `census_pending` に留める。
  理由は上の 2 条の合成である——**1 回の evaluate は構造上 1 水準しか見ない**
  （「M2e カテゴリを含む report の level は単一」を fail-closed で要求しているため）
  ので、そのコールから 4 水準 × 2 アーム = 1280 セルの census を立証する術が無い。
  立証できない以上、判定の語を出してはならない。帯の判定は **r6/r7 の水準横断集計**
  が census を満たしたときに出す（その集計器は `aggregate_m2e_census`（CLI `--census`）
  として実装済み）。

### 6.3 routing — 追加1件（既存メニューは1件も変えない）

`_ROUTES["full_mix"]` に `crepe_direct` は入っていないため、direct アームを
`input_kind: "full_mix"` では表現できない。`"clear_lead"` を使えば引けるが、**入力は明白に
フルミックスであり、素材の宣言が虚偽になる**（`V_direct` が `clear_lead` を名乗れたのは、
実際に clear lead だったからである）。よって:

```python
"full_mix_direct_probe": [
    MelodyRoute("crepe_direct", _PRE_NONE, _EXT_CREPE),
],
```

- 意味: 「フルミックスを、分離を通さず直接抽出器に当てる」＝ direct アームが測っている
  対象そのもの。素材を偽らずに表現できる唯一の形。`INPUT_KINDS` にも追加する。
- **必須テスト:** 既存4キー（`vocal_track` / `clear_lead` / `full_mix` /
  `chord_pad_no_melody`）の route 列が**追加前と完全一致**すること。
- **必須テスト:** `full_mix_direct_probe` を参照するのが `_CATEGORY_SPECS` の
  `V_remix_real_direct` 行のみであること。
- **`_ROUTES` の既存キーへの route 追加は引き続き禁止**（`full_mix` に `crepe_direct` を
  足す案は M1 / M4 の選択挙動を変えうるので却下）。加算的な新キーのみ許す。

## 7. 主生産物と宣言する限界

### 7.1 主生産物 — 破断曲線

**`V_remix_real_direct` の破断曲線**：主旋律の支配度がどこまで下がると `crepe_direct` の
音高追跡が壊れるか。水準軸に沿った単調性が素材によらず成立するため、この曲線は
**素材間の外挿仮定なしに読める。** ここが本帯の唯一の主張可能領域。

**`V_remix_real_stem` の水準応答**は副生産物として全点提示する。単調性を仮定しないので
「曲線」ではなく「4点の実測値」として扱い、傾向の外挿を書かない。

**M4 との接続（本帯の存在理由）:** `clear_lead` と `full_mix` の差は本質的に主旋律の
支配度であり、破断点が +12dB 側に寄るなら `crepe_direct × clear_lead` の実測
（M4 G2 の本命）は成立の見込みがある。0dB 側で既に割れているなら実運用素材でも同じか
それ以下。**曲線は実運用帯の校正を与えないが、校正を試みる価値の有無を教える。**

### 7.2 限界（レポートに必ず併記）

- **歌声と伴奏は別の曲である。** vocadito の声と MUSDB18-HQ の伴奏は調性もテンポも
  無関係。実運用（同一曲の声と伴奏）に比べ和声的に不整合であり、抽出が**易しくなるか
  難しくなるかは一意に決まらない**。方向が決まらない以上、**「実伴奏を使ったから実運用帯を
  満たす」とは主張できない。**
- したがって本帯の結果を根拠に `V_fullstack` へ昇格させない。昇格を狙うなら URMP
  （注釈出自の確認待ち・声なし）か MedleyDB 申請再開のいずれかであり、本書の範囲外（§12）。
- ベッドは MUSDB18-HQ test split の先頭2曲であり、**ジャンル・編成の代表性は主張しない。**
- **+12dB は実運用のミックス balance ではない。** トリップワイヤ専用の人工的水準である。

## 8. 実測の規模と実行

### 8.1 構造は削らない（先に固定する）

規模の話に入る前に、**資源がいくらであっても削らないもの**を確定する。ここを曖昧に
したまま時間から逆算すると、「入る形」に科学が合わせられてしまう。

| 軸 | 値 | 削らない理由 |
|---|---|---|
| clip | **40 件（全件）** — 両アーム同一集合 | 両アームが同一集合なので、アーム差と標本差の交絡が構成上発生しない |
| ベッド | **2** | 1本では破断点が crepe の性質か当該ベッドの性質かを区別できない。素材非依存性の最小構成 |
| 水準 | **4点**（+12/+6/0/−6 dB） | 破断曲線そのもの。点を減らせば曲線が曲線でなくなる |
| アーム | **2**（direct / stem） | direct は主生産物、stem は §5.4 で診断専用から引き上げた判定対象 |
| 反復 | **n = 2** | `repeats_min: 2` は凍結済み。**本書はこれに触れない** |
| **総セル数** | **40 × 2 × 4 × 2 × 2 = 1280** | §6.2 の manifest 展開と一致すること |

**規模は科学が決め、実行時間はスケジューラが決める。** 両者を結んではならない
（附録A-5）。実行時間を理由に上表を削ることは、§8.8 の User 決裁を経る場合を除き禁止。

### 8.2 上限は1回の実行にかける

**`B_session = 2.0 時間`**（1回の実行の壁時計上限。7200 秒）

- これは**1回の実行にかける上限**であり、実験全体の予算ではない。
- 総セル数 1280 は `B_session` の値に**依存しない。**
- したがって `B_session` は**いつ変更してもよい**（r2-0 の前後を問わない）。変更しても
  測るものが変わらないから。§8.5 のシャード地図を未完セルについて引き直すだけである。

### 8.3 並列度 `P` と並列不変性ゲート

- `P` = 同時実行ワーカープロセス数。各ワーカーで `OMP_NUM_THREADS=1` /
  `MKL_NUM_THREADS=1` / `torch.set_num_threads(1)` を**固定**する。スレッド数は
  リダクション順序を変えうるため、**決定論の前提条件であり性能設定ではない。**
- 初期値は `P = 物理コア数`。r2-0 で OOM / swap / 劣化が出たら `P ← P − 1` として
  r2-0 をやり直す。**試行はすべて記録する。**
- 劣化判定: `P` 並列時の1セルあたり壁時計が `P = 1` 時の **1.5 倍を超える**なら飽和と
  みなし `P` を1つ下げる。
- `P` は `env_digest` に**含めない**（結果に影響しないため）。ただし**セルレコードには
  必ず記録する**（コスト再現のため）。

**並列不変性ゲート（実行前の必須確認）** — 並列化が結果を変えないことは主張ではなく
確認事項である。

- r2-0 のセルから **2 セル**を選び、`P = 1` と `P = 決定値` の両方で実行する。
- **合格条件: 出力ピッチ軌跡の sha256 が完全一致**（精度値の一致では不十分。丸め後に
  一致していても軌跡が違えば別条件である）。
- **不一致なら並列実行を禁止**し、`P = 1` で §8.5 を計算し直す。その結果 §8.8 の回数上限を
  超えるなら User 決裁へ差し戻す。
- この2セルは**校正・確認の専用**であり、精度値を本測定に流用しない。

### 8.4 r2-0 — 単位コストの校正

規模を決める前ではなく、**シャード幅を決める前に**、実測で単位コストを確定する。
測るのは production と同じ `P` で回したときの**1セルあたり壁時計**である。

- **`S`**: プロセスプールの起動〜モデルロード完了までの固定コスト（秒）。シャードごとに
  1回だけ発生する。
- **`T_direct`**: direct アーム `2P` セルを `P` 並列で流したときの `(壁時計 − S) / (2P)`。
- **`T_stem`**: stem アーム `2P` セルについて同様。
- いずれも **2 波（2P セル）以上**を回して求める。1波だと最も遅いセルが平均を支配し、
  シャード幅を過小に見積もる。
- **単位コストはコンテナ実体に固有である（rev.6 追加）。** r2-0 実測で、同一セルの壁時計
  が別インスタンス間で **2.2 倍**、同一実行内のセル間で **1.42 倍**ばらついた。よって
  `T_*` は「一度確定して以後使い回す量」ではない。**各セッションの開始時に 2 波を回して
  `T_*` を測り直し、§8.5 の地図を未完セルについて引き直す。** これは §8.5 が既に許して
  いる手続きの明文化であって、新しい自由度ではない。前セッションの `T_*` をそのまま
  次セッションへ持ち越すことを**禁止**する。
- 併せて確定・記録: `env_digest`（§8.7）、`n_max`（§3.5）、`P`、並列不変性ゲートの結果。
- **r2-0 の全セルの精度値は本測定の結果に含めない。** 本測定で同一セルを改めて回す。
  校正と本測定を兼ねると「早く終わった条件」が本測定に混ざる。

### 8.5 シャード幅とラベリング（自由変数なし）

```
cap = 0.85 * B_session - S           # 0.85 は変動・後片付けの余裕。凍結値
cost(cell) = T_direct  if cell.arm == "direct"  else  T_stem

order = 全1280セルを (bed_id, level, clip_id, arm, repeat_idx) の lexical order で整列
s = 0 ; acc = 0
for cell in order:
    c = cost(cell)
    if acc > 0 and acc + c > cap:
        s += 1 ; acc = 0
    cell.shard_id = s
    acc += c
N_shards = s + 1
```

- 余裕係数 **0.85 は凍結**する。実測が速かったからといって上げてはならない（上げれば
  「もう1セル入るはず」の判断が実行中に混入する）。
- 入力（`T_direct`, `T_stem`, `S`, `B_session`）が同じなら**出力は一意**。裁量の余地はない。
- 確定した **`cell → shard_id` の全対応表**を `m2e_r2_shard_map.yaml` として
  **本測定の開始前に commit する。**
- **`cap <= 0` または `cap < max(T_direct, T_stem)` の場合**: 1セルすら1回に収まらない。
  本測定は開始せず、`S` / `T_*` / `P` を添えて User 決裁へ差し戻す。

**シャード地図は科学ではなくスケジューリングである。**

> **セル台帳（どのセルが存在するか）は不可侵。
> シャード地図（どのセルをどの回に回すか）は再計算してよい。**

`P` / `S` / `T_*` / `B_session` が変わった場合、**未完セルについてのみ**再適用して地図を
引き直す。**完了済みセルのレコードは影響を受けない**（セル結果はシャード割り当てに
依存しない）。再計算のたびに旧地図と新地図の diff を dated 記録する。
**セル台帳そのものを再計算してはならない**——台帳を触った瞬間、これはスケジューリング
ではなく規模の変更になる。

### 8.6 1回の実行の契約

- **1回 = 1シャード。** 実行は `shard_id` を引数に取り、その shard のセルのみを対象とする。
- shard 内のセルは**動的キュー**でワーカーに配る（静的等分ではない。遅いセル1本で
  ワーカーが遊ぶのを避けるため）。配布順は §8.5 の order に従う。
- **新しいセルを開始してよいのは `elapsed + cost(cell) <= B_session` のときのみ。**
- 実行中のセルが `B_session + 600 秒`（ハングの絶対上限）を超えたら打ち切り、
  **「未完」として記録する**（失敗値を書かない）。
- shard が時間内に終わらなくても**延長してはならない。** 未完セルは次回の実行で
  §8.7 の digest 一致判定によりそのまま再開される。
- **超過は異常ではなく、設計に織り込まれた通常状態である。**
- `shard_id` の昇順で実行する。飛ばしてよいのは、その shard の全セルが digest 一致で
  完了済みの場合のみ。
- **実行中に規模を変えてよい経路は存在しない**（附録A-6）。

### 8.7 チェックポイント・再開・環境同一性

「単一セッションで完走できない」への正しい答えは、**規模を1セッションに縮めることでは
なく、セッション境界を無意味にすること。**

- 実行単位は **1 セル** = `(clip_id, bed_id, level, arm, repeat_idx)`。
- セル完了ごとに結果レコードを **atomic write**（`src/svp_rpe/utils/atomic_io` を流用。
  新しい書き込み機構を作らない）。レコードに含めるもの: 入力 digest（mix の
  `waveform_sha256`・注釈 sha256・重み digest）、`env_digest`、精度値、所要秒、`P`。
- **再開規則:** レコードが存在し、かつ入力 digest と `env_digest` が一致するセルは
  スキップする。いずれかが不一致なら**スキップせず、不一致の事実を記録して再実行**する。
- **`env_digest`** に含めるもの: Python 版、torch / demucs / crepe / librosa / soundfile /
  numpy の版、demucs 重み digest、crepe 重み digest、スレッド設定、
  **CPU 同一性（モデル名 + 命令セットフラグ。rev.6 追加 — §8.9.3）**。r2-0 で確定し、
  同時に **lockfile を commit する**。再開時は lockfile から環境を再構成し、
  `env_digest` を再計算して一致を確認する。
- **`env_digest` 不一致のまま継続してはならない。** 一致させて再開するか、不一致を記録
  した上で当該帯を最初から回し直すかの二択。**複数環境のセルを1つの帯として合算することは
  禁止。**
- **実行環境を User 機へ移すことは禁止しない。** ただし移すなら **r2-0 からやり直す**
  （`env_digest` と単位コストが変わるため）。帯の途中で環境を跨ぐことのみを禁止する。

### 8.8 実行回数の上限と、標本削減の唯一の入口

- **`R_max = 12 回`**（`N_shards` の上限）を宣言する。
- **`N_shards > R_max` となった場合、本測定を開始しない。** `S` / `T_direct` / `T_stem` /
  `P` / `N_shards` を添えて User 決裁へ差し戻し、次の3択を提示する:
  1. `R_max` を引き上げる（規模は不変。回数だけ増える）
  2. 実行環境を変更して `P` を上げる（r2-0 からやり直す）
  3. **clip 数を削る** — このときのみ、休止中の縮退手順（附録B）が発動する。
- **3 は自動発動しない。** 標本削減は User の明示的決裁を経由する経路以外に存在しない。

### 8.9 evaluate（外部検証）フェーズ — `B_eval` を宣言しない（rev.6）

r6 直前の実測で、evaluate が **1 起動 10.0 h・不可分・再開不能**であることが判明した。
実行側から「`B_eval` を独立の予算単位として宣言する」案が出たが、**採らない。**

#### 8.9.1 `B_eval` を宣言しない理由

- **予算の宣言は能力を作らない。** `B_session = 2 h` がコンテナの実体上の上限であるなら、
  設計文書に `B_eval = 12 h` と書いても 12 時間のセッションは手に入らない。§8.2 が
  `B_session` を「いつでも変更してよい」としているのは、**環境が供給できる範囲内での
  再配分**を許す趣旨であって、供給量そのものを宣言で増やせるという意味ではない。
- **分散を考えると、どんな予算でも足りない。** §8.4 で観測した 2.2 倍のインスタンス間
  分散を 10.0 h に掛けると 22 h。安全側に取れば `B_eval` は 26 h 級になる。
  **再開不能な 26 時間ジョブは、予算を宣言しても運用できない。**9 時間目の失敗で全損
  する構造は、`R_max` が防ごうとしたものそのものである。
- **§8.7 と矛盾する。** §8.7 は「セッション境界を無意味にすること」を正しい答えと定め、
  再開規則をセル粒度で既に規定している。evaluate が再開不能なのは**設計の欠落ではなく
  実装の未達**であり、設計を曲げて実装に合わせる理由がない。

#### 8.9.2 代わりに要求する実装性質（2点）

**(1) 検証専用ストアによる再開可能化。**
evaluate が再開できない根拠は「キャッシュを自分自身と比較することになる」であった。
これは**ストアが1つしかない場合にのみ**正しい。分ければ成立しない。

```
run フェーズ      → store_A に書く / store_A のみ読む
evaluate（検証）  → store_B に書く / store_B のみ読む   ← run の結果は一切読まない
publish 条件      → store_A と store_B を突き合わせる（両方とも完全な独立計算）
```

evaluate が `store_B` の自分の途中結果から再開することは、**独立性を損なわない**。
損なうのは `store_A` を読むことだけである。したがって `--cell-store` を積まない現在の
禁止は `store_A` に対してのみ維持し、`store_B` に対する再開を実装する。

再開の可否は **`env_digest` の一致で fail-closed** に判定する（§8.7 の再開規則をその
まま適用）。`store_B` の途中結果が別環境で作られていたら再開せず、記録して回し直す。

**(2) evaluate の並列化。**
evaluate が 10.0 h かかるのは、逐次実行（実質 `P = 1`）だからである。実測 254.2 s/セル
と 10.0 h / 160 セル = 225 s/セルが一致することがこれを裏づける。
**publish 条件が要求しているのは「fresh process であること」と「run の結果を読まない
こと」であって、逐次であることではない。** run フェーズを `P = 4` で回しながら検証だけ
`P = 1` を要求するのは一貫しない — 並列度が結果を変えるなら、run フェーズの側が先に
疑われる。並列不変性ゲート（§8.3）が担保しているのはまさにこの点である。

`P = 4` を効かせれば 10.0 h → 約 2.9 h。(1) と併せて、evaluate は run フェーズと同じ
形（数時間・再開可能・セル粒度）になり、**`B_session` の変更も環境変更も不要になる。**

#### 8.9.3 `env_digest` に CPU 同一性を含める

§8.4 の 2.2 倍分散は**スケジューリングの問題として現れたが、再現性の問題でもある。**
現行の `env_digest` は版とスレッド設定を畳むが CPU を含まないため、**命令セットの異なる
CPU（AVX2 / AVX-512 等）で走った 2 つのセルが、同一の `env_digest` を持ちうる。**
数値経路が分岐した場合、それを検出する手段が無い。

よって `env_digest` に **CPU モデル名と命令セットフラグ**を含める（§8.7 に反映済み）。
これは code change であり、**r6 は code change を禁じているため r6 開始前に landing
させる**必要がある（F2 と同じ論法）。既存の pin（`bed_window_sha256` 等）はハッシュ対象
そのものが変わらないため無効化されない。`env_digest` の値は変わるので、変更日を記録する。

#### 8.9.4 実装ノート（2026-08-02・C2/C3 landing 時の設計判断 D-1/D-2/D-3）

§8.9.2 の 2 点（store 分離・evaluate 並列化）を実装するにあたって確定させた 3 つの
判断を、根拠つきで記録する。**§8.9.1〜8.9.3 の本文・凍結値・閾値は変更していない。**

**D-1. 並列不変性ゲートが比較する artifact = `est_trajectory_sha256`（M2e row 限定）。**
§8.3 のゲートは「`P=1` と `P=決定値` で**推定ピッチ軌跡が完全一致**」を要求するが、
実装には比較対象そのものが無かった（row には `est_frame_count` /
`est_voiced_frame_count` と指標値しか無い）。**精度値の一致では代替しない**——平均化・
丸め・フレーム集計を経た指標は、軌跡が違っても偶然一致しうる。

採用: `_est_trajectory_sha256`（`scripts/run_melody_accuracy.py`）を新設し、
**M2e カテゴリ（`bars_file == m2e_accuracy_bars.yaml`）の `outcome == "measured"` の
clip row にだけ**刻む。全カテゴリへ足す案は却下——既存 M2b/M2c の commit 済み記録と
突き合わせるテストが期待値差分で割れ、そこで schema を広げて吸収する誘惑が生じる。
テスト専用機構に留める案も却下——r4（r2-0）は**実 run に対して**ゲートを回す手順で
あり、永続フィールドが無ければ回せない。`unavailable` の row には**キーごと置かない**
（測っていない軌跡に sentinel を置かない）。

直列化仕様（`m2e-est-trajectory/1`。docstring とテストで pin）: マジック →
`struct.pack("<Q", n)` → 各フレーム `struct.pack("<dd", time, freq)`。**float の
`repr()` / JSON 表現は使わない**（テキスト表現はプラットフォームで揺れうる）。
`-0.0` は `0.0` へ正規化し、非有限値と長さ不一致は fail-closed。

**D-2. `--workers` は run phase と evaluate phase で意味が非対称である。**
C2/C3 以前の `--workers` は**両フェーズで記録専用**だった（help: 「実行そのものは
変えない」）。C3 で **evaluate phase のみ実効並列度**にし、**run phase は逐次のまま
据え置く**。理由: run 側のスケーリングは §8.5 のシャード地図（`m2e_r2_shard_map.yaml`）
が担う設計であり、run の実行形態を今変えると r4 で校正する `T_*` の意味が変わる。
この非対称は help 文・`run_accuracy` / `evaluate_m2_bars` の docstring・
`_run_external_category` のコメントに明記し、run が逐次であることは
`test_run_phase_clip_loop_stays_sequential_even_with_many_workers` が pin する。

**宣言された限界**（PR #240 Codex P1 で顕在化）: 1 カテゴリの測り直しは `repeats_min`
本の子しか起こさないため、実効並列度は **`min(P, repeats_min)` で頭打ち**になる。
凍結 `repeats_min = 2` なので `--workers 4` でも実効 2 であり、§8.9.2-(2) の見積もり
「10.0 h → 約 2.9 h」ではなく **10.0 h → 約 5.0 h** が現状で得られる値である。
`2.9 h` へ届かせるには repeat より下の粒度（clip / シャード / カテゴリ）の並列化が要り、
それは「1 子プロセス = 1 カテゴリ row」という測り直しの成果物の形と、その row を
提出 row と bit 比較する publish 条件の形を変える——**本実装の範囲外・別ブリーフ**
（C5 と同じ扱い）。実効値は verdict の
`evaluate_execution.effective_workers_per_category` に刻み、黙って頭打ちにしない。

並列化の実装は `concurrent.futures.ThreadPoolExecutor(max_workers=P)` で
**既存の `subprocess.run` を最大 P 本同時に保つ**形（`ProcessPoolExecutor` は使わない
——測定は既に別プロセスで走っており、in-process の worker プロセスを挟むと
fresh-process 契約が曖昧になる。ここのスレッドは子の完了を待つだけで測定はしない）。
結果は `index` 順の固定席へ書き戻し、失敗も**最小 index のものを再送出**する
（どのエラーが表に出るかが `P` に依存してはならない）。

**D-3. スレッド 3 点固定は run と evaluate で同一でなければならない（最大のリスク）。**
検証の子だけを `OMP=1 / MKL=1 / torch=1` に固定すると、固定していない run が産んだ row と
bit 一致しなくなる。publish 条件は「独立に測り直して bit 一致」なので、**ここが割れると
r6 が丸ごと通らない**（HANDOFF §3.1 の裏返し）。

採用: `--pin-threads` を **run phase / evaluate phase の両方**に露出する（条件そのものは
同一だが、フェーズで役割が分かれる）。

- **run phase**: `_apply_thread_pinning()` でこのプロセスに固定を適用し、その事実を
  report の `thread_pinning` に刻む。env 2 点は**設定せず検査する**——OpenMP/MKL の
  スレッド数はランタイムのロード時に確定するため、プロセス開始後に `os.environ` を
  書いても効かず、「固定したと report に書きながら実際には未固定で測る」最悪の形になる。
  3 点目（`torch.set_num_threads(1)`）は適用したうえで `torch.get_num_threads()` で
  効いたことを確認する。
- **evaluate phase**: 評価器は**何も測らない**ので自プロセスには固定を適用しない
  （測定に関係しない torch import で `_require_scorer_compile_observation_covers_
  imported_modules` などの自己ゲートを揺らさないため）。代わりに (a) 評価対象 report が
  名乗る固定を**契約として検証**し（`_thread_pinning_contract_from_reports`。全 report で
  一致すること + `OMP/MKL == "1"` かつ `torch_num_threads ∈ {1, 未導入マーカー}` の
  形であること）、(b) 子へ env 2 点 + `--pin-threads` を渡し、(c) 子 report の
  `thread_pinning` 申告を親が再照合する（**宣言されているが検証されていない値を作らない**）。
  契約を評価器の状態でなく report から導くのは、**束縛時点と使用時点を一致させる**ため
  ——子へ渡すべき条件は「提出 row を産んだ run の条件」である。

`--pin-threads` 未使用時は run も evaluate も従来どおり（新フィールドゼロ）で、
run↔evaluate の条件は「どちらも未固定」で一致する。

**D-4. `store_A` との重なり検査は CLI ではなく「評価対象 report」に対して置く**
（PR #240 Codex P1 で是正）。当初は `--cell-store` × `--eval-cell-store` の 2 引数を
比較していたが、**evaluate phase は `--cell-store` 自体を拒否するので、その分岐は本番の
呼び出しでは一度も走らない**。一方 run report は `cell_store_relative` を刻んでいるため、
その値を `--eval-cell-store` に渡すことは実際にできてしまい、鍵
`(category, level, entry_id, repeat_index)` が一致する run のセルを子がそのまま resume
する——「独立に測り直して bit 一致」が**自分自身との比較**に化け、F2 で塞いだ穴が別の
入口から開く。よって関所は `evaluate_m2_bars` に置き、**評価対象 report が名乗る store**
との同一性・入れ子を resolve 後に拒否する。`cell_store_relative` が `None`（repo 外の
store で走った run）は重なりを立証も反証もできないので fail-closed にする。

併せて、`store_B` の木に評価入力（report / manifest member / fixtures / provenance 対象の
ソース）が含まれる指定も拒否する。子は `store_B` 配下へ `cell_<digest>.json` を atomic
replace で書くため、名前の一致した入力を置き換えて自分の証拠を壊しうる。関所は
「起こりうる出力名を列挙する」形ではなく「保護入力が木の中に無いことを要求する」形に
置く（出力名の集合はセル鍵の数だけあり、列挙は関所として脆い）。

**D-5. パスの分離は計算の独立を意味しない——役割をレコード自身に束縛する**
（PR #240 Codex P1 で是正）。D-4 の経路検査は「`store_B` が `store_A` と別の場所にある」
ことしか言えない。`store_A` を別ディレクトリへ**コピー**すれば経路検査は通り、
コピーされたレコードは `_cell_record_mismatches` の同一性フィールドを**全部**満たす
——鍵・入力・環境・生成器 digest がそのまま一致し、とくに `repeat_index` は run の
`0..n-1` と測り直しの `0..repeats-1` が正面から衝突する。結果、検証の子が run のセルを
resume し、publish が再び自己比較になる（F2 で塞いだ穴の三度目の入口）。

よってセルレコードに **`store_role`（`run` / `evaluate`）を必須フィールド**として持たせ、
役割の不一致を resume 拒否事由にする（schema `m2-cell-record/0.3 → 0.4`）。測り直しの子には
評価器が `--cell-store-role evaluate` を自動で付ける。**役割を名乗らない旧レコードも
resume しない**——素性の分からないセルを通さない。

「store ごとの一意識別子」ではなく役割にしたのは、識別子だと store の初期化手順
（ID の生成・保管）に依存し、その手順を飛ばした store が黙って通る余地が残るため。
役割は書き手が常に知っている値なので、初期化に依存せず全レコードに必ず入る。

> 独立性の関所は 3 層になった: **(1) CLI の引数関係**（同一・入れ子）→
> **(2) 評価対象 report が名乗る store との関係**（D-4）→ **(3) レコード自身の役割**（D-5）。
> (1) と (2) は「どこに置いたか」、(3) は「誰が計算したか」を問う。前者だけでは
> コピーで抜けられる。

**D-6. シャード実行機（C6・§8.6 の実行契約）は既存のセル測定・記録経路を「呼び出す」
だけで、新しい書き込み経路を作らない。** 実装（`scripts/run_melody_accuracy.py`）は
`generate_m2e_shard_map`（§8.5 の凍結擬似コードの逐語実装。地図 YAML に
入力値・fixtures 4 本の sha256・`cell → shard_id` 全対応表・`N_shards`・生成時刻を
記録し、同一入力からバイト一致で出る）と `execute_m2e_shard`（1 shard の実行機）に
分かれる。5 点を記録する:

- **セル測定は `_measure_or_resume_external_clip_row` の per-cell 呼び出しに一本化**
  （`_shard_measure_and_record_cell`）。レコードパス・書き込みは
  `_cell_store_record_path` / `svp_rpe.utils.atomic_io` をそのまま共有し、
  `store_role` は常に `run`（D-5 の役割区分をそのまま踏襲）。これが resume 互換
  AC（既存の「1 水準まるごと」run phase が shard 実行機の書いたセルを resume できる）
  の根拠であり、セルレコード schema（`m2-cell-record/0.4`）へのフィールド追加は
  ゼロ。
- **動的キューは常に multiprocessing（spawn context）を経由する**（`P = 1` でも）。
  §8.4 の `S`（プロセスプール起動〜モデルロード完了）という定義、および
  「実行中セルが `B_session + 600s` を超えたら**実プロセスを `terminate()` して**
  打ち切る」という契約の両方が、in-process 呼び出しでは実装できない（Python の
  通常の関数呼び出しは安全に強制中断できない）ため。打ち切り時点で in-flight
  だったセル（trigger したセル自身を含む）は「打ち切り」として shard 実行記録に
  残し、セルレコードは書かない（`terminate()` が実プロセスを kill するため、
  書き込み完了の保証がない——「セルレコードを書かず、未完として記録する」の
  実装上の帰結）。
- **開始許可式 `elapsed + cost(cell) <= B_session` の `elapsed` は親の単調クロック**
  （`time.monotonic`）で測り、配布は §8.5 order を厳守する動的キュー（1 セルずつ）。
  ある1セルが許可式を満たせず拒否されると、それ以降のセル（より安価でも）へは
  進まない——bin-packing ではなく「配布順は §8.5 order に従う」の実装。
- **ワーカーは env_digest を自分で再計算し、親の期待値と一致しなければそのセルを
  開始しない**（`_shard_worker_measure_cell`）。不一致は shard 実行を即座に中断する
  例外として扱う——ハング打ち切り（正常終了として記録）とは別の、環境不整合による
  fail-closed 停止。スレッド 3 点固定は env 2 点をプロセスプール起動前に親側で検証し、
  `torch.set_num_threads(1)` は各ワーカーの `initializer` 内で適用する（決定済み
  設計判断 5 のとおり）。**モデル preload も同じ initializer 内で行う——E-50 参照
  （2026-08-02 時点の初版実装ではここを「スレッド固定のみ」としていたが、その判断は
  誤りとして撤回した）。**
- **campaign ファイル**（`m2e-campaign/0.1`）はパスのみを持つ（各水準の external
  manifest / external fixtures の所在）。地図の読み込み・実行開始前に、campaign が
  指す fixtures を現在の committed 実体と再照合し（`_require_m2e_shard_map_matches_
  registry`）、欠け・重複・余剰のいずれも fail-closed にする——セル台帳（fixtures が
  決める 1280 セルの集合）は不可侵、シャード地図（どのセルをどの回に回すか）だけが
  再計算可能という §8.5 の規律を実行時にも立証する。

キュー/許可式/打ち切りの機構テストは picklable な top-level fake
（`tests/_shard_queue_fakes.py`）を実 multiprocessing（spawn）へ注入して検証する
——このモジュールは意図的に `run_melody_accuracy` を import しない。fake が
`run_melody_accuracy` を import 済みのモジュール（本体・テストファイルとも）に
居ると、spawn の子プロセスが pickle された callable の `__module__` を import し
直すたびに同じ重い import 連鎖（本環境で実測 ≈24 秒/回）を再生し、テスト全体が
実用的でなくなることを実測で確認した。resume 互換を確かめるテストは
`_shard_measure_and_record_cell` を multiprocessing を経由せず直接呼ぶ（fake
backend 統合テストは P=1 の in-process 経路で行うという Test Strategy どおり）。

#### 8.9.5 実装ノート（2026-08-02・C5 水準横断 census 集計）

§6.2 が「帯の判定は `gate_level` の run が §11 のセル census を満たしたときにのみ出る」と
定め、2026-08-01 の実装ノートが「その集計器は未実装」と宣言していた穴を埋める。
**`aggregate_m2e_census` が帯の判定を出す唯一の場所である。**

**E-1. 入力は verdict であって run report ではない。** report から再判定すると
`evaluate_m2_bars` の全ゲート（測り直しによる独立検証・provenance 照合・pin 束縛）を
二重実装することになり、2 つの判定経路が食い違う余地を作る。verdict は既にそれらを
通過した成果物なので、集計器は「揃っているか」だけを問う。

**E-2. 期待セル数は積として再計算する。** `1280` を定数で書かない
（`_m2e_census_expected_cells` = コホート幅 80 × ラダー長 4 × アーム数 2 × `repeats_min`）。
定数はコホート・ラダー・アーム・repeats のどれかが動いたときそれを黙って通すが、積は
必ず食い違う（§6.2「総抽出回数の一致確認。一致しない実装は誤り」）。

**E-3. census が揃うまで metrics を成果物に存在させない。** §11 は部分集合での平均 RPA・
途中の破断曲線・見通しの表明を禁じている。「出さない」ではなく**文書に存在させない**
ことで、下流が偶然読んでしまう経路ごと消す（`band_verdict` / `level_response` は
`null`、`cells` は件数のみ）。テストは census 文書の全 bytes に `raw_pitch_accuracy` /
`metrics` 等が現れないことを固定する。

**E-4. 環境同一性を要求する。** §8.7 の「複数環境のセルを 1 つの帯として合算することは
禁止」を水準横断の集計面へそのまま適用し、全 verdict の `env_digest` 一致を fail-closed で
要求する。そのため `evaluate_m2_bars` は M2e verdict に `env_digest` を刻む（M2e を含む
verdict のみ・加算。単一性は従来から要求済みで、値を成果物へ持ち出しただけ）。
**運用上の含意**: 4 水準を別インスタンスで測ると CPU 差で `env_digest` が割れ、census は
揃わない（§8.4 の 2.2 倍分散はこの形でも現れる）。これは不便ではなく、§8.7 が要求している
ことそのものである。

**E-5. 通過しても昇格しない。** `promotes_route` / `unlocks_m4_g2` を常に `false` として、
`declared_limits`（§7.2 の 4 点）とともに**成果物へ埋め込む**。読み手が設計文書へ戻らなく
ても、この帯が何を解錠しないかが判定と同じ場所にある。

**E-6. アーム間の同一性は id ではなく素性の hash で問う**（PR #241 Codex P1 で是正）。
当初はアーム間で `clip_ids` の一致だけを見ていたが、**id は名前であって bytes ではない**
——2 つの manifest が同じ 80 個の id を持ちながら別世代の音声・別世代の登録簿を指す
ことはありうる。row は既に `external_manifest_sha256` / `external_fixtures_sha256` を
運んでいるので、その 3 つすべての一致を要求する。

**E-7. census の分母を verdict の自己申告に決めさせない**（PR #241 Codex P2 で是正）。
`repeats_min` は期待セル数（分母）を決めるので、verdict が `1` を名乗れば半分終わった帯が
「揃った」ことになる。集計器は**自分で読んだ基底バー**から `repeats_min` を取り、verdict の
申告はそれとの一致を要求するだけにする。同じ理由で `bars_sha256`（共有スカラーの供給元）
も凍結ファイルと照合し、CLI は `--out` が基底バーを潰さないよう保護する
（当初は `m2e_bars` だけを照合・保護しており非対称だった）。

**E-8. 水準横断のコホート同一性を要求する**（PR #241 Codex P1 で是正）。E-6 のアーム間
照合は**同一水準の中しか見ない**ため、水準ごとに fixtures 世代が違えば各水準は 80 件を
満たしながら**別の 80 件**でありうる——破断曲線が別コホートの寄せ集めになる。id 規約
`vremix_{clip_id}_{bed_id}_{level_tag}` の水準タグを剥がした**正規化コホート**で 4 水準を
突き合わせる。あわせて、各水準の id が**その水準のタグ**で終わることも要求する
（`level: "+6dB"` を名乗る verdict が `p12` の id を運んでいれば、同じミックスを 2 回
測って別水準として並べたことになり、曲線が 1 水準の複製から組み上がる）。

タグ検査は件数と独立に行い、正規化結果を水準横断照合に使うのは per-cell 検査を通った
セルだけにする——短いコホートを「別コホート」と報告すると本当の原因（件数不足）が
見えなくなるため。

**E-17. 「全部欠けている」を「揃っている」と見なさない**（PR #241 Codex P1 で是正）。
E-13 の等値検査は `verdict.get(field)` を比べるので、**全 verdict がそのフィールドを
持たなければ `None` 同士で一致**し、照合はフィールドを剥がすだけで無効化できた。
`env_digest` には形の要求（64-hex）を置いたのに builder provenance には置いていない、
という非対称。dict であることと 3 つの digest が sha256 であることを要求する。

> 同質性検査を「値が揃っているか」だけで書くと、**不在は常に揃う**。証拠を要求する
> フィールドには、比較の前に**存在と形**を課す必要がある。

**E-19〜E-21. E-17 の一般則を全証拠フィールドへ適用し切る**（PR #241 Codex P1×2 + P2 で是正）。
E-17 は builder provenance だけを塞いだが、同じ論法——**不在は常に揃う**——が当たる箇所が
3 つ残っていた。(1) `numeric_runtime_config`: `env_digest` が `threadpool_info` を畳まない
宣言された穴は、この記録の照合を前提に許容されている——記録なしでは前提が成立しない。
存在と非空 dict を要求する。(2) アーム対の `external_manifest_sha256` /
`external_fixtures_sha256`: 両アームが揃って欠けば `None == None` で対の照合が空転する。
per-cell 検査で 64-hex sha256 を要求する（raise ではなく `problems` へ——E-11 の裁定どおり
部分測定は報告する）。(3) 共有スカラー（`tolerance_cents` / `est_voiced_confidence_floor`）:
成果物へそのまま載せる値なので有限数値を要求する（E-14 と同じ規律・これは自己点検で発見）。

CLI の未使用フラグ拒否（E-15）も**値比較では不完全**だった——`--workers 1` のような
既定値の明示指定は検出できない。センチネル既定値（`_ARGPARSE_UNSET`）で「渡されたか」
そのものを追跡し、census phase では既定値と同じ値でも渡された事実を拒否する。
census 検査の直後にセンチネルを実既定へ正規化し、run/evaluate 経路へ漏らさない。

**E-22. 帯判定セルの gate_level を凍結条件と束縛する**（PR #241 Codex P1 で是正）。
セルの選択は verdict の自己申告（top-level `level`）に依存しているため、category 側の
`gate_level` 申告も凍結値（`conditions[arm]["gate_level"]`）と束縛しなければ、別水準で
当てたバーの結果が帯の判定として publish されうる。`bar_satisfied` を使う前に要求する。

**E-23. 凍結閾値を census 自身が metrics へ再適用する**（PR #241 Codex P1 で是正）。E-18 は
`bar_satisfied ↔ failures` を束縛したが、**metrics ↔ 判定**は誰も束縛していなかった。
metrics だけを書き換えれば「凍結バーを割る metrics を `level_response` に載せながら
pass を出す」成果物が組めた。census 自身が読んだ凍結バーを evaluate と同一の比較方向
（`min_rpa` は < / `max_vfa` は > / `max_octave_gap` は >）で再適用し、`bar_satisfied`
との一致を要求する。**derived failures の文字列照合はしない**——E-18 が
`bar_satisfied↔failures` を、本検査が `metrics↔bar_satisfied` を束縛すれば連鎖は閉じ、
失敗文字列の形式へ結合するのは brittle で over-engineering という裁定（per-cell 検査で
`repeats_bit_identical is True` を既に要求しているため、bit 不一致由来の failure が
band ループへ混入する経路も無い）。

**E-24. numeric_runtime_config のキー集合を生成側の形と束縛する**（PR #241 Codex P1 で
是正）。E-19 の「非空 dict」検査は `{"unknown": true}` のような placeholder を通してしまう。
生成側（`_numeric_runtime_config()`）が実際に返すトップレベルキー集合を凍結定数
`_NUMERIC_RUNTIME_CONFIG_REQUIRED_KEYS` として持ち、束縛する。census 内で producer を
直接呼ばないのは、計測 instrumentation（threadpoolctl 等）の import を評価器プロセスへ
持ち込まないため——代わりにテスト
(`test_numeric_runtime_config_required_keys_match_the_producer`) が producer との機械
同期を enforce する。`generator_code_sha256` は既に現 checkout と照合済みのため、生成側
の形が世代間で動いてもこの検査が誤爆する経路は無い。

**census の保証境界の宣言**（PR #241 Codex 第 7 巡「Validate runtime configuration
values」・E-30。見送り裁定）。E-19（存在）→ E-24（キー集合）→ 本指摘（値・ネスト構造の
検証）と、同じ指摘が 1 段ずつ深くなった。ここで境界を宣言する: **census の保証は
(1) 自分が publish するフィールドの形と相互整合、(2) 合算可否を決める証拠フィールドの
verdict 間 byte 等値 + 形（キー集合まで）+ 凍結ファイル・現 checkout への pin、である。**
値・ネスト構造まで producer schema を複製して検証することは、evaluate のゲートの二重
実装（E-1 で却下）へ漸近し、かつ偽造耐性は増えない——bars/generator/evaluator の pin を
実値でコピーする偽造者は、値スキーマも同様にコピーできる。偽造に対する実根拠は
`verdict_pins`・dated record・evaluate の独立測り直しであり、census はその上の readback
整合層である。以後、この境界の内側の指摘は採用し、外側は本宣言を参照して見送る。

**E-25. 公開 census bytes の pin を stdout へ残す**（PR #241 Codex P2 で是正）。書き込みに
渡すのと同一の snapshot から sha256 を導出し、`census sha256: <hex>` として stdout へ出す
（`json.dumps` の二重実行も同時に解消）。本リポジトリの計測 runbook は stdout を
`*_stdout.txt` として dated record に保存する既存の流儀なので、この pin はそこに残る。
文書内への自己埋め込みは自己言及（hash が自身を含む bytes を対象にできない）になるため
せず、sidecar ファイルの新設も本段階では過剰と判断した（裁定）。runbook 側でも stdout
保存をコマンドに組み込んだ（E-29）。

**E-40. stdout の保存先を per-run の日付つきファイル名にする**（一部採用・PR #241
Codex P2 で是正）。**採用**: 固定名 `census_stdout.txt` は `tee` が truncate で開くため、
再実行が census の fail-closed 拒否で落ちても、`census.json` は残るのに前回の正当な
pin 記録だけが消えるという破壊経路があった。`census_stdout_$(date -u
+%Y%m%dT%H%M%SZ).txt` へ変更し、成功した実行の `census.json` と対で commit する運用に
した。**見送り**: JSON と digest を 2 ファイルまとめて atomic に publish する staging
機構。`census.json` 自体は既に atomic write で digest 行は書き込み後に出るため、
「新 census が pin 無しで残る」のは `tee` 自体の書き込み失敗（コマンド全体が非ゼロで
終わり操作者が再実行する状況）に限られる。per-run 命名で再実行が破壊なしに両方を
再生成できる以上、2 ファイル横断の atomicity は runbook の 1 ステップに対して過剰
（E-25/E-29 の sidecar 見送りと同じ判断）。

**E-41 追記**（一部採用・PR #241 Codex P2）。同一秒の**逐次**再実行（自動リトライ等）

**E-26. 共有スカラーを凍結バーの実値と束縛する**（PR #241 Codex P1 で是正）。E-19 の
有限性検査だけでは、verdict が「50 cents で測った」と自己申告した metrics をそのまま
publish できてしまう——E-7（`repeats_min`）で自分が適用した規律との非対称だった。

**E-27. 平均で保存される metric 不変条件のみ census で再適用する**（スコープ限定採用・
PR #241 Codex P1 で是正）。まず `_require_metrics_contract` を census の平均済み
metrics へそのまま適用する実装を試したが、**通らなかった**——evaluate は external
カテゴリで contract を **clip metrics** にのみ適用し、census が持つカテゴリ平均
metrics（`_average_external_clip_metrics` の出力）には `_require_finite_metrics` しか
課していない（`voiced_chroma_correct_frame_count` が算術平均で非整数 float になり

(a) `metrics.tolerance_cents == 凍結値`（clip 間の一致が前提のため平均でも保存）、
(b) `raw_chroma_accuracy >= raw_pitch_accuracy`（非負差の平均は非負）、
(c) `octave_gap == raw_chroma_accuracy - raw_pitch_accuracy`（平均は加減算と可換）。

**E-28. repeat 間の bit 一致を必要条件として再検査する**（必要条件のみ採用・

相互 bit 一致していることは、boolean 申告と独立に検査できる。

**E-32. clip_ids 要素の非文字列破損をクラッシュでなく census_incomplete として報告する**

**E-34. 巨大整数 metrics の OverflowError クラッシュを census_incomplete として報告する**
（PR #241 Codex P2 で是正）。400 桁級の JSON 整数（`isinstance(value, int)` は真だが
`float(value)` が表現できない）が metrics に入ると `float()` 変換が `OverflowError` を
投げ、`except ValueError` を素通りして census 全体がクラッシュしていた（E-31/E-32 と
同型）。`except` を `(ValueError, OverflowError)` へ拡大し、E-33 の一般コードで報告する。

事前検査で塞ぐには float 変換の意味論を複製することになる——だから except を広げる。

**E-18. `bar_satisfied == not failures` を読み戻しで再検証する**（PR #241 Codex P2 で是正）。
`evaluate_m2_bars` はこの不変条件を確立するが、集計器は読み戻し時に一度も検証して
いなかった。型（E-16）が正しくても関係が壊れていれば、`true` + 非空 `failures` は
**失敗の証拠を同梱したまま pass を publish** し、逆は理由の無い fail を publish する。
**型を要求しただけでは足りない——値どうしの整合も要求する。**

**E-16. 帯の判定を導く値は bool そのものを要求する**（PR #241 Codex P2 で是正）。
`bar_satisfied is None` を通しただけでは `"false"` のような**非空文字列が残り、真偽評価は
真になる**——**fail が pass として publish される**、この機構で最悪の失敗形である
（しかも起こる場所は「帯の判定を出す唯一の場所」）。`load_verdict` は bytes 束縛と
top-level schema しか見ないので、category フィールドの型は集計器が独立に要求する。
成果物へそのまま載せる `failures` も同様に list であることを要求する。

**E-13. 混合式の provenance を水準横断で照合する**（PR #241 Codex P1 で是正）。
**破断曲線は主生産物であり、混合式が水準間で混ざれば曲線として成立しない。** ところが
水準ごとに fixtures ファイルは別なので `external_fixtures_sha256` の水準横断比較は意味を
持たず、mixer（`make_vremix_fixtures.py`）を変えて一部の水準を作り直しても、id は同じ・
per-level hash は元々違う・harness のコード pin は mixer を含まない、で誰も気付けなかった。
fixtures 自身が名乗る `builder`（run 側で `_require_registered_m2e_cohort` が実体照合済み）を
verdict へ写し、集計器が水準横断の一致を要求する。

> **「現行 mixer とも一致していること」までは要求しない。** ミックスの音声 bytes は
> fixtures の sha256 で既に pin されており、測定の正しさは mixer の現在値に依存しない。
> 現行一致まで求めると、完了済みキャンペーンが後日の無関係な mixer 変更で無効になり、
> 「一度測って後で集計する」という本トラックのモデルと衝突する。

**E-14. `metrics` の形を、成果物へ載せる前に確かめる**（PR #241 Codex P2 で是正）。
`load_verdict` は top-level schema と bytes 束縛しか見ないので、`metrics` が欠損・`null`・
短縮でも他の per-cell 検査は全部通り、`census_complete` を出したうえで `level_response` に
欠測が載る（帯の判定だけは `bar_satisfied` から出る）。`repeats_min` 件の有限数値である
ことをセルを数える前に要求する。なお **NaN / inf はさらに手前**（`_json_loads_no_dup_keys`
の非有限リテラル拒否）で落ちるため、ここで扱うのは有限値の欠損・短縮である。

**E-15. census が読まない引数はすべて拒否する**（PR #241 Codex P2 で是正）。
census が実際に読むのは `--census` / `--out` / `--bars` / `--m2e-bars` の 4 つだけ。
`--external-manifest` 等を黙って無視すると、渡した側は「census がその manifest に束縛
された」と信じうる——成果物はそれを一度も読まない。当初の検査は 5 フラグしか見ておらず、
コメントの主張（「run/evaluate のどのフェーズ引数とも組み合わせない」）より実装が狭かった。

**E-12. コホートの一意性を件数と別に要求する**（PR #241 Codex P2 で是正）。
`len(clip_ids) == 80` だけでは、80 要素あっても重複していれば**異なる測定は 80 未満**で
あり、`observed_cells` は重複を数える。全水準・全アームで同じように重複していれば E-6 /
E-8 の等値検査も通るため、**1280 の異なる測定なしに「1280 セル完了」を報告できてしまう**。
`load_verdict` は受け取った bytes を hash するだけで一意性を証明しないので、集計器が
独立に要求する。

**E-10. `numeric_runtime_config` も水準横断で照合する**（PR #241 Codex P1 で是正）。
`env_digest` は **`threadpool_info` を意図的に含めない**（計測のための threadpoolctl
import が scoring の pin へ混入するのを避けるため）。その穴は「記録は
`numeric_runtime_config` に残るので事後の原因帰属はできる」という前提で**宣言された穴**
として許容されている——**その記録を照合しなければ前提が成立しない**。evaluate は 1 水準の
中で `_require_homogeneous_numeric_runtime_config` を既に課しているので、水準を跨ぐ集計
だけが弱いという非対称になっていた。同質性の検査対象に加える。

**E-11. アーム間照合は per-cell 検査を通ったセル同士でのみ行う**（PR #241 Codex P2 で是正）。
片アームが `insufficient_repeats` で欠けている水準は「**部分測定**」であって「別素材」では
ない。完了したアームの値と欠けたアームの `None` を突き合わせて raise すると、**census が
本来出すべき `census_incomplete` の報告そのものが出せなくなる**——部分測定を報告するのが
census の目的なので、ここで落としてはならない。E-8 の水準横断照合と同じ扱いに揃える。

**E-9. 書き出す直前に load 時 pin の不変を再確認する**（PR #241 Codex P2 で是正）。
run / evaluate と同じ post-execution ガード（`_require_unchanged_since_load()`）を census の
`_atomic_write_text` 直前にも置く。集計中にソースが差し替わると、census は「現 checkout と
一致する」と検査したはずのコード pin を名乗りながら、実際には別 bytes の下で組まれた
成果物になる。

その他の関所: (level, arm) の重複拒否（コピーした verdict で census を埋めさせない）、
`m2e_bars_sha256` は verdict の自己申告ではなく**集計器が読んだ凍結ファイル**と照合、
`generator_code_sha256` / `evaluator_code_sha256` は現 checkout と 3 段照合。

CLI: `--census VERDICT.json...`（`--evaluate` とは排他。run/evaluate のフェーズ引数は
すべて fail-closed）。

**r4/r6 の運用**: 本測定は run・evaluate ともに
`OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 ... --pin-threads` で起動する（runbook §5 以降）。

#### 9.1 pin の三層と、`archive_sha256_local` の穴の扱い

pin は同じ強さの一枚岩ではなく、**三層**である。混ぜると穴の所在が見えなくなる。

| 層 | 対象 | 誰の主張か | 現状 |
|---|---|---|---|
| (1) 配布物 | Zenodo 公開 md5 | **公開者**の主張の転記 | 記録済み |
| (2) ローカル容器 | `archive_sha256_local` | 我々の算出 | **算出不能（部分取得）** |
| (3) 復号内容 | 各 stem の `stem_sha256` | 我々の算出 | **これから完備させる** |

**荷重を受けているのは (3) である。** 測定が依存しているのは zip という容器ではなく、
復号されたサンプル列だからだ。したがって:

- **r2 を `archive_sha256_local` で止めない。** 22.7 GB の完全取得は (3) を強くしない。
- 代わりに **(3) を採用2件だけでなく、スクリーニングした全50曲について完備**させる。
  選定の監査可能性は「通過2件」ではなく「全50件の記録」に載っている（§3.3-2）。
- **(2) は `null` と dated 理由で明示的な穴として残す。** 空欄で放置しない、推定値を
  書かない、上流 md5 を転記して埋まったことにしない。**宣言された穴は穴のままでよい。
  黙って塞がったように見せるのが不正である。**
- 部分取得でも成立する帰属証拠として、zip **中央ディレクトリの CRC-32・member path・
  非圧縮サイズ**を各 member について記録する。完全アーカイブを持つ第三者は、我々が
  容器ハッシュを持たなくても「これは配布物の member である」を照合できる。取得済み
  範囲から中央ディレクトリが読めない場合は `unavailable` と理由を書き、`member_sha256`
  と size のみを記録する（**穴をさらに宣言する**のであって、埋めたことにしない）。

#### 9.2 `canonical decode` の定義（凍結）

「canonical decode 後の sha256」と書きながら decode を定義していなかった。定義する。

```
canonical decode (ソース stem 専用):
  reader     : soundfile / libsndfile — バージョンは env_digest に記録
  dtype      : ファイル固有の PCM 整数幅のまま読む（float 変換しない）
               int16 → int16 / int24 → int32（上位詰め・スケーリング禁止）
  resample   : 禁止。native rate != 44100 なら fail-closed で停止
  channel    : そのまま（downmix・チャンネル並べ替え禁止）
  layout     : C 連続・shape (n_frames, n_channels)・little endian
  stem_sha256 = sha256(np.ascontiguousarray(x).tobytes())
```

**float を pin の中に入れない理由:** 整数 PCM を float へ落とすときの除数（32768 か
32767 か）はライブラリで割れる。float 化を pin に含めると、pin が外部ライブラリの内部
規約に依存する。**float 変換は §4 の生成手続きに属し、pin の外に置く。**

これは §4.6 が生成物に対して凍結している `waveform_sha256`（float32 の `tobytes`）と
**衝突しない**。生成物はもともと float32 なので除数の曖昧さが存在しない。
**ソース stem は native 整数で pin、生成ミックスは float32 で pin** — 対象が違うので
どちらも変更しない。

**CI（音源不要）:** 数十サンプルの int16 wav を fixture として commit し、canonical decode
の結果が既知 sha256 と一致することを検証する単体テストを置く。ライブラリ更新で復号が
変わったらここが赤くなる。§4.8 と同じ方針（実素材なしで規約だけを守る）。

**トレードオフの明示:** 合成ベッドは spec + コードだけで完全再現できた。実ベッドは
**外部素材の可用性に再現性が依存する**。realism を取って reproducibility を一段落とす
交換であり、**runbook はこの落差を埋めるための必須装備であっておまけではない。**

#### 9.3 実行環境は揮発する — 資産の再プロビジョニングは `S` に含める

slow-lane のコンテナは回収されうる。**資産が消えることは異常ではなく既定**として扱う。

- **`S`（§8.4 のセットアップ費）に資産の再取得・重み配置を含める。** §8.5 の
  `cap = 0.85 * B_session - S` が既にこれを吸収する。`S` 単独で `B_session` を超える
  場合は §8.5 の fail-closed に該当し、User 決裁へ差し戻す。
- **重い取得は r2 の一度きり。** 全 50 曲が要るのはスクリーニングだけで、r3 以降に必要な
  のは**採用 2 曲 × 3 stem + vocadito 40 clip** のみ。これは数百 MB 規模であり、
  毎回の `S` に乗せても本測定を圧迫しない。
- r2 の計算自体も窓 `[0, n_max]`（約 34 秒）に限られる。**重いのは取得であって計算ではない。**
- **既存 pin を再取得の検証に使う。** vocadito は `m2c_external_fixtures.yaml` に
  zip md5 と 40 clip の sha256 が事前登録済み。再取得のたびにこれで照合し、
  **一致しなければ停止**する（再取得は §13 の「vocadito の再取得・再エンコード」禁止に
  当たらない — 禁止しているのは**別バイト列で差し替えること**であって、pin 一致を
  確認した復元は同一物の回復である）。
- **資産が無いことは設計の欠落ではなく provisioning の欠落。** r0 の runbook
  （§10 P-a）がこの穴を塞ぐ唯一の装備であり、後回しにしてよい成果物ではない。

## 附録A — 撤回・是正の記録（監査対象）

いずれも **`m2e_accuracy_bars.yaml` へ1行も書かれておらず、M2e の実測は0件**の時点での
差し替えである。よって「凍結の緩和」ではなく「**登録前の設計差し替え**」であり、
one-way rule の対象外。この事実を M2e-r0 の dated 記録に明記すること。

### A-1. 改訂1（合成ベッド `V_remix_synth_*`）— 撤回

改訂1 は「**実ベッドが調達できない**」を前提にした前哨だった。調査
（`RESEARCH_medleydb_alternatives.md`・2026-07-31）でこの前提が崩れた
（MUSDB18-HQ が無申請・DOI つき・150曲・stem 分離済みで直接入手できる）。合成ベッドを
使う理由が消えたため、`V_remix_synth_direct` / `V_remix_synth_stem` は登録前に撤回。

**存続する裁定:**

- **「V_fullstack として押し通す」の却下理由。** `m2_accuracy_bars.yaml` は既に
  `S_fullstack: {}` を凍結しており、これは「バー未定」ではなく「**合成伴奏込みの
  フルスタックには判定バーを置かない**」という決定である。別素材をその昇格バーで
  判定することは、閾値を動かさずに**閾値が守っていた素材の定義を動かす**行為であり、
  one-way rule が禁じる緩和の変種にあたる。**ベッドが実音源になっても、
  「歌声と伴奏が同一曲ではない」ため同じ理由がそのまま生きる**（§7.2）。
- **見返りがないという理由。** M4 の `CALIBRATION_BOUND_ROUTES` は `{"crepe_direct"}`、
  G2 の帯は `clear_lead`。M4 が待っているのは crepe_direct × clear_lead の校正であって
  demucs→crepe × V_fullstack ではない。
- **runbook 必須。** 素材が変わっても「実行者は交換可能」という要件は不変（§10 M2e-r0）。
- **水準ラダー4点と「主生産物は破断曲線」。** 素材依存の設計ではないためそのまま存続。

### A-2. 親設計の単一帯 `V_remix`（バー 0.65/0.10・2水準）— 2アームへ置換

分離器を通す経路と通さない経路では、測っているものの信頼性が根本的に違う。
単一帯では両者が混ざる。§5 の2アーム構成へ置換（登録前）。

### A-3. 旧スクリーニング指標 `voiced_frame_ratio <= 0.10` — 退役

**声なし素材が声あり2件の間に入った。** 判別器は反例1つで死ぬ。閾値をどこへ動かしても
分離できない以上、これは「バーが厳しすぎた」ではなく「**測っている量が違った**」。
一方向規律が禁じるのは**有効な閾値の緩和**であって、**無効な計器の廃棄ではない。**

原因: crepe は音高追跡器であり、安定した器楽ほど高い有声率を返し、ビブラート・子音・
息継ぎのある歌声ほど低く出る。**この指標は歌声の存在に対して単調ですらない。**

閾値 0.10 は**導出せずに置いた推測値**だった。**設計側の不備であり、実行側に落ち度はない。**

**退役記録の必須項目**（`docs/measurements/` へ dated 記録）:

- 11 素材の `voiced_frame_ratio` 実数値、**全件**（採否ではなく生値）。
- 声なし素材が声あり2件の間に入るという**順序そのもの**の明示。
- 掃引の範囲と 11/11 不採用（0.5097〜0.8769）という結果。
- **測定窓**: 約180秒の短尺クリップであった事実と、**曲頭からの開始オフセット**。
  0.0s 起点ならミックス窓の上位集合として有効。0.0s 起点でないなら、この11件は
  「旧指標に判別力がない」ことの証拠としてのみ残し、窓の議論からは切り離す
  （退役の結論は窓に依存しないため変わらない）。
- **「全50曲は旧指標では意図的に回していない」という明示**と理由（退役済みの計器に
  2.5時間を払わない）。生値を残すので、疑う者は自力で反証できる。

**新指標では全50曲を回す**（§3.3-2）。180秒基準の2.5時間は `n_max` ≈ 34 秒窓なら約1/5に
落ち、器楽漏れ床の変動はこの全件分布でしか埋まらない。閾値は導出値として凍結済みなので、
測る数を増やしても規律に触れない。

### A-4. 補正1 §8 の帯ブロック — 是正

補正1 §8 は `gate_level` / `levels` / `level_margin_db` を**バー block の中**に置き、
`_REQUIRED_BAR_KEYS_BY_CATEGORY` に含めるよう指示した。しかしバー block の各キーは
`_BAR_THRESHOLD_RANGES`（`min_rpa` / `max_vfa` / `max_octave_gap` のみ・有限数値・値域つき）で
fail-closed 検証されるため、**文字列 `"+12dB"` もリストも通らない。** 通すには
`_BAR_THRESHOLD_RANGES` を「閾値の値域表」でないものに変質させるしかなく、それは検査の
弱体化である。

原因は分類の誤り: **バーは judge が数値比較する閾値、`gate_level` / `levels` は「何を
測ったか」の宣言**であって、別の種類の対象である。§5.3 の2 block 構成へ是正。
**閾値の値は1つも動いていない。**

### A-5. 補正2 §3（総予算 12 時間からの規模逆算）— 撤回

補正2 は `B = 12 時間` を**総予算**として置き、そこから clip 数 `k` / `m` を逆算した。
つまり**「資源上限」を「科学の規模」に直結させた。** その構造だと資源が減るたびに測る
対象が痩せる。

正しい分解は「**上限は1回の実行にかける。規模は削らない。足りない分は回数で埋める**」
（User 決裁 2026-08-01・§2 の⑤）。規模（何セル測るか）は科学の側の量、実行時間
（1回に何秒回すか）はスケジューリングの側の量である。§8 で結合を切った。

切った帰結として **`B_session` は科学的パラメータではなくなり、いつでも変更してよい数に
なった**（§8.2）。また `k = m = 40` に復元されたため、補正2 §4.2 が防いでいた
「アーム差と標本差の交絡」は構成上発生しない。

### A-6. 改訂2 §6-3 の縮退規則（clip を lexical 先頭20件へ）— 撤回

あの規則は「1セッションに収まらない」への対処だったが、§8.7 のチェックポイント再開で
その問題自体が消えた。規模は時間切れではなく §8.1 の台帳で先に決まるので、
**実行中の縮退という概念を廃止する。** 実行中に規模を変えてよい経路は存在しない。

加えて、lexical 先頭切り出しは**それ自体が誤り**だった。vocadito の id 順が歌手・出典で
並んでいた場合、先頭切り出しは素材の偏りをそのまま拾う。標本削減が必要になった場合は
附録B の系統抽出を使う。

### A-7. 統合正本に残っていた未指定 3 件 — 是正（2026-08-01）

統合の時点でなお**規則を書かずに運用されていた**3 点を、実行側の指摘により閉じた。
3 件とも「実行側が妥当な選択をしていた」ことは確認しているが、**妥当な選択が
書かれていないこと自体が欠陥**である（書かれていなければ次の実行者が同じ選択に
到達する保証がない）。

1. **`lexical order` の照合方式が未定義**（§3.3-1・§8.5 の両方で使用）。UTF-8 バイト列
   辞書順として定義（§3.3.1）。UTF-8 の性質により、実行側が凍結値として採用中の
   codepoint 順と**恒等**なので既取得順序の引き直しは発生しない。あわせて、`level` を
   文字列辞書順で並べると物理量と無関係な順序になる欠陥を発見し、`ladder_index` での
   整列に是正した。**本測定が 1 セルも走っていない時点なので、この確定は無償**である。
2. **`archive_sha256_local` 未算出・`canonical decode` 未定義**。pin を三層に分解し
   （§9.1）、荷重が容器ではなく復号内容にあることを明示。(2) は `null` + dated 理由の
   **宣言された穴**として残し、代わりに (3) を全50曲へ完備させ、部分取得でも成立する
   帰属証拠（member CRC-32 + `member_sha256`）を追加した。`canonical decode` は native
   整数のまま hash する形で定義し（§9.2）、float 除数の曖昧さを pin の外へ出した。
   **完全取得を r2 の前提条件に格上げしない**（22.7 GB を落としても (3) は強くならない）。
3. **スペクトログラム未生成**。期限を「r3 まで」から **「r2 の内側で閉じる」**へ締めた。
   一方向オーバーライドが清潔なのは音高結果を見ていないことに依存しており、測定開始後の
   棄却は結果を見た棄却と外形が区別できない。あわせて、**棄却事由 (a)〜(e) を画像を見る
   前に dated 事前登録**する規則と、画像本体を commit しない規則を追加した。
   指摘のとおり**採用2件を生成後に倒すことは規定上可能**であり、その経路を閉じるのではなく
   **裁量が入らない形に整形**した（事由の事前列挙・順序の次点への自動繰り上げ）。

### A-8. 棄却事由 (d) の無音定義 — 提示3案を却下し導出値を採用（2026-08-01）

rev.2 で (d) を「連続 1.0 秒以上の無音・欠落」と書きながら**無音を数値で定義しなかった**。
実行側が3案（厳密ゼロ / −60 dBFS_peak / −80 dBFS_peak）と**各案が落とすトラック**を
添えて決裁を求めた。

**この決裁の形そのものが危険である。** 3案は「どれを選ぶと採用ベッドがどうなるか」が
既に見えている状態で提示されており、ここで案を選ぶ行為は**結果を見て閾値を選ぶ**ことに
外形が一致する。実行側に落ち度はない（定義を書かなかったのは設計側）。

したがって **3案から選ばない**。(d) の目的（宣言水準の局所的な不成立を捕まえる）から
**既宣言パラメータのみで導出**し、判定結果が未知の定義を立てた（§3.4.6）。導出値は
`-26.0 dB relative to bed_active_rms` で、§3.4.2 の残留ボーカル閾値と**同じ定数・同じ
基準量**である。新規自由パラメータは 0 個。

peak 基準を却下した理由は、peak が本設計のどこにも宣言されておらず、かつ 1 サンプルで
決まる量だから。厳密ゼロを却下した理由は、本設計が全域で水準相対に書かれており絶対
ゼロ基準が宣言されていないから。

**設計側の自己拘束:** §3.4.6 の判定結果は本裁定の時点で未知であり、**どの結果でも
受け入れる**。気に入らないことを理由に定義を差し替える経路は §13 で閉じた。
両方棄却でも損失は pin 順序を下へ進むことだけである。

### A-9. (d) の判定閾値が実装で −40 dB になっていた — 是正（2026-08-01）

M2e-r2 の実装は (d) の判定に **−40 dB** を用いた。正は **−26.0 dB**（§3.4.6）。
−40 dB は §4.3 の active フレーム判定＝`bed_active_rms` を作るためのゲートであり、
判定閾値ではない。§3.4.7 に明確化を追記した（内容変更なし・再言）。

**原因は設計側にある。** 裁定を要約した際の「§4.3 の凍結済み無音定義を流用」という
文言が、実際には「フレーム条件 2048 / 512 と、基準量 `bed_active_rms` を算出する
ためのゲート」を指していたのに、**判定閾値そのものを指すとも読める**書き方だった。
実行側は両方の定義で計算し、実装側で選ばずに設計へ差し戻した。これは正しい対応で
あり、落ち度はない。

**一方向規則との関係（重要）:** 是正の向きは **緩和ではなく厳格化**である。
−26 dB は −40 dB より多くのフレームを dropout と数えるため、(d) 該当は
**29/50 → 32/50 へ増える**。実測を見た後に閾値を**厳しい側へ**戻す是正であり、
かつ戻し先は rev.3 で凍結済みの値そのもの（新しい選択を一切していない）。
したがって §13 の「見てから緩める」禁止には抵触しない。

**採用 2 件は両定義で同一**（[02] Angels In Amplifiers / [03] Arise - Run Run Run）
であり、選定のやり直しは発生しない。−40 dB 版の集計は**削除せず**、実装が一時
−40 dB であった事実として日付つきで r2 報告に残す（消すと、なぜ 2 通りの数値が
存在するのかを後から説明できなくなる）。

### A-10. `B_eval`（evaluate 専用予算）の提案を却下 — 実装で塞ぐ（2026-08-01・rev.6）

r2-0 校正の実行報告で、**evaluate（外部検証）フェーズが 1 セッションに収まらない**
（必要 `B_eval` ≳ 11.8 h）ことが判明し、実行側から「`B_session = 2 h` は run 用に
据え置いたまま、evaluate を独立の予算単位 `B_eval` として宣言する」案が上がった。

**却下する。** 理由は §8.9.1 に書いた3点で、要旨は次のとおり。

1. **予算の宣言は能力を作らない。** `B_eval = 12 h` と書いてもコンテナの上限が
   2 h なら 12 h のセッションは生まれない。宣言は不足の記述であって解決ではない。
2. **どの予算値でも不足する。** 同一セルの壁時計が別インスタンス間で **2.2 倍**
   ばらつく（下記）。安全側の `B_eval` は 26 h 規模になり、しかも中断復帰できない
   26 h ジョブは 9 時間目の失敗で全損する。予算では吸収できない。
3. **§8.7 と矛盾する。** §8.7 は既に「セッション境界を無意味にする」＝セル粒度の
   中断復帰を要求している。evaluate が復帰できないのは**設計の欠落ではなく実装の
   欠落**であり、設計側の裁定で埋めるべき穴ではない。

代わりに §8.9.2 で**実装要件を2つ**立てた。(i) evaluate は run とは別の store
（`store_B`）に書き、`store_A` を一切読まない — publish の独立性は「store を分ける」
ことで保たれるのであって「復帰できない」ことで保たれるのではない。(ii) evaluate を
`P = 4` で回す。evaluate が 10.0 h かかっているのは逐次実行（実効 `P = 1`）だから
であり、publish が要求するのは新プロセスと `store_A` 非参照であって逐次性ではない。
run を `P = 4` で回しながら検証だけ `P = 1` を要求するのは、§8.3 の並列不変ゲートが
まさにその同一性を検査している以上、一貫しない。`P = 4` で 10.0 h → 約 2.9 h となり、
`B_session` の変更も実行環境の変更も不要になる。

**併せて2件を是正した。**

- **`env_digest` に CPU 同一性を追加（§8.7・§8.9.3）。** 同一セルが別インスタンスで
  254.2 s → 552.4 s（2.2×）、同一実行内のセル間で 1.42× ばらついた。これは
  スケジューリングの不便である前に**再現性の欠陥**である。現行の `env_digest` は
  版とスレッド設定を畳むが CPU を畳まないため、AVX2 実体と AVX-512 実体で数値経路が
  分かれても digest 上は区別がつかず、「同一環境として合算してよい」と誤判定しうる。
- **`T_*` のセッション跨ぎ再利用を禁止（§8.4）。** 単位コストはコンテナ実体に固有で
  ある以上、`T_direct` / `T_stem` は一度確定して使い回す量ではない。各セッション開始
  時に2波を回して測り直し、未完セルについて §8.5 の地図を引き直す。

**r6 との時間関係（F2 と同じ論法）:** 上記の実装3件（`store_B` 分離、evaluate 並列化、
`env_digest` への CPU 追加）は **r6 開始前に landing させる**。r6 は code change を
禁じているため、r6 に入ってからでは入れられない。

**波及:** run フェーズの「7 シャードで収まる」という結論も同じ 2.2× を継承する。
10.1 h は 22 h でありえ、その場合 `N_shards` は約 15 で `R_max = 12` を超える。
よってこの数字は確定値として扱わず、§8.4 の再校正規則の下でセッションごとに
引き直す。

## 附録B — 休止中の手順（§8.8 の User 決裁でのみ発動）

`N_shards > R_max` で User が「clip 数を削る」を選んだ場合にのみ、以下が発動する。
**自動発動はしない。**

### B-1. 導出可能性の規律（常時有効・休止しない）

> **スクリーニング閾値は、宣言済みの実験パラメータから導出できる場合にのみ事前登録する。
> 導出できないものは事前登録せず、校正実測を先に立てる。**

測定バー（RPA / octave gap 等）の凍結規律は**一切変えない**。二本立てにすること:

| 種別 | 規律 |
|---|---|
| 測定バー | 実測前に凍結・**実測後に緩めない**（従来どおり） |
| スクリーニング閾値 | **導出可能性が事前登録の要件**。推測値の凍結を禁止 |

混ぜないことが肝。「バーは緩めない」と「スクリーニングは導出できるものだけ凍結する」は
別の規律である。

### B-2. 系統抽出（lexical 先頭 k 件ではない）

```
direct_set = [ clips[ floor(i * 40 / k) ] for i in 0 .. k-1 ]      # 40 件から系統抽出
stem_set   = [ direct_set[ floor(j * k / m) ] for j in 0 .. m-1 ]  # direct の部分集合
```

`stem_set ⊆ direct_set` が構成上保証される。確定した id 列を `m2e_bed_fixtures.yaml`
へ pin する。

### B-3. アーム間比較の制限

`k > m` のとき、direct(k件) と stem(m件) をそのまま並べると**アームの差と標本の差が
交絡する**。よって:

- **アーム間の比較・差分の提示は `stem_set`（m件）に限る。**
- direct アームの破断曲線（主生産物）は **`direct_set`（k件）**で別途提示する。
- 同一の表に k 件系列と m 件系列を混在させない。件数を各行に必ず併記する。

### B-4. 精度低下の宣言

`k < 40` のとき、平均 RPA の標準誤差は **√(40/k) 倍**に広がる。`m` 側はさらに広い。
**この倍率を記録に明記する**（例: k=24 なら 1.29 倍、m=8 なら 2.24 倍）。
「小さい標本で測った」ことを読み手が補正できる形にする。

なお stem アームの唯一のゲートは `gate_level: "+12dB"` の単点トリップワイヤであり、
精密な推定を要求しない。壊れていれば大きく割れ、健全なら大きく上回る。
**m が小さいことはトリップワイヤの機能を損なわない。**
