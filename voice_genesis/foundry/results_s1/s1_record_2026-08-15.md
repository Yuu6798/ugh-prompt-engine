## run 2 の発散事故（正直会計）

run 2（bf16-mixed・grad clip 1.0 での resume）も step ~5300-5400 帯で発散した。
run 1 の「fp16 AMP 勾配オーバーフロー」説（`MixedPrecision.scale: 0.0`、上記
「run 1 の発散事故」節）は run 2 には**当てはまらない**。以下 3 点を実測（Pod
`train.log`）で確認し、fp16 原因説を棄却する:

1. **bf16 実効**: `train.log` に bf16 混合精度での実行が記録されており、
   fp16 では動いていない（run 1 と異なるプレシジョン経路）。
2. **scaler キー無し**: bf16 パスは GradScaler を使わないため、checkpoint に
   `MixedPrecision.scale` キー自体が存在しない（run 1 の「scale=0.0 に張り付き」
   という直接証拠が run 2 には構造的に存在しえない）。
3. **clip 1.0 受理**: 勾配クリッピング（`gradient_clip_val=1.0`）は設定どおり
   受理されて機能していた（クリップが無効化されていた形跡なし）。

発散の形は**突発型**: `mel_loss` は step 5300 時点で `0.1041`（健全な低下
トレンドの範囲内）だったのが、直後の step 5400 で NaN に転じている。緩やかな
発散ではなく、単一 step 相当の急変。

  系列後半で破綻＝末尾フォノーム ID への勾配が常にゼロ）。

  （pin `e2307b1`）の `DsBatchSampler.__form_batches()` は `np.random.default_rng()`
  を**シード引数なし**で呼んでおり、`seed` コンストラクタ引数は内部キャッシュ
  キー（`self.formed`）判定にのみ使われ乱数生成には一切使われない。したがって
  実行間でバッチ順序（=どのサンプルがどの step に来るか）は本質的に非決定論的
  であり、「run 1・run 2 とも同一の病的バッチが同一 step に来て発散した」という
  素朴な仮説はコードレベルで**反証**される。
- **改訂 causal picture**: 上記より、単一の「病的サンプル/バッチが原因」説は
  弱まった。より整合的な仮説は、bf16/AMP 特有の汎用的な数値不安定性が
  LR スケジュールのある地点（ピーク帯）付近で、たまたま危険な組成（§3.1 の
  4 件を含みうる長尺/無音過多なバッチ）を引いた場合に**確率的に**発火する、
  というもの（run 1・run 2 が異なるバッチ順序を経験したにもかかわらず類似の
  step 数で発散した観測とも整合的）。特定/断定はできないため、以降は
  「LR ピーク帯 × 危険バッチ組成の確率的事故」という仮説をワーキングモデルと
  して扱う。
