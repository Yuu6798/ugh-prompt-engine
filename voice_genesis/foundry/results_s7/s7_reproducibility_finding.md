# 再現性の実測と pin 意味論の訂正（2026-08-22）

コンテナ再構築で作業ディスクが消えた復旧の過程で、**「何を pin すれば再現したと
言えるのか」**が実測で 1 段はっきりした。結論を先に書く:

> `samples_sha256`（波形バイト同一性）は**再 export を跨ぐと成立しない**。
> しかし**測定値は全軸で ε の内側**に再現する。守るべき性質は後者であり、
> 前者は同一プロビジョニング内の完全性検査として残す。

## 1. 何を再取得し、何が一致したか

`provision.sh` で 17 資産を pin 照合つきで再配置し、3 世代の ONNX を再 export した。
run7 の資産 9 件を旧 manifest の pin と照合:

| pin | 状態 |
|---|---|
| `acoustic_dsconfig_yaml` / `acoustic_phonemes_json` / `speaker_embed` | ✅ 一致 |
| canon linguistic / dur / pitch / vocoder / phonemes.txt | ✅ 一致 |
| **`acoustic_onnx`** | ❌ **不一致** `f0e71f06…` → `cb1c590b…` |

同一 checkpoint・同一 config（sha 照合済み）・同一 torch 2.13.0+cpu / onnx 1.22.0 で、
**同じ export 実行から出る他の 3 成果物は一致している**。したがって差は入力ではなく
**ONNX グラフのシリアライズ**にある。

## 2. その差は波形に出るか（出る。ただし最下位ビット規模）

校正 14 刺激を再レンダして比較:

| 検査 | 結果 |
|---|---|
| `samples_sha256` | **一致 1 / 不一致 13**（一致したのは合成ゼロ緩衝 = レンダではない） |
| `peak_raw` の最大差 | **1.49e-08** |
| `rms_raw` の最大差 | **1.58e-09** |

float32 の最下位ビット規模である。

## 3. 測定値は動くか（**動かない**）

凍結済み spec の `reference_output` を再レンダで測り直した:

| 軸 | 1.0 max\|Δ\| | 1.1 max\|Δ\| | ε | 比 |
|---|---|---|---|---|
| `excess_tail_voiced_ms` | **0** | **0** | 10 ms | — |
| `release_after_score_boundary_ms` | **0** | **0** | 10 ms | — |
| `tail_f0_persistence` | **0** | **0** | 0.0333 | — |
| `terminal_mel_persistence` | 2.97e-07 | 2.97e-07 | 0.0387 | **ε の約 1/130,000** |

voicing 3 軸は**完全一致**（有声判定はフレーム単位の離散量なので、最下位ビットの差では
判定が変わらない）。mel 軸だけ 1e-7 規模で動くが、ε より 5 桁小さい。

**したがって 1.0 / 1.1 の凍結値も、360 セルの測定値も、この環境で有効である。**
仕様の再凍結は要らない。

## 3b. 本番 360 セルでも同じ（voicing 3 軸は完全一致・mel のみ ε の 1/270）

校正 14 刺激だけでなく、**本番 360 セルを再レンダして旧測定値と照合**した:

| 軸 | max\|Δ\|（360 セル） | ε | 比 |
|---|---|---|---|
| `excess_tail_voiced_ms` | **0** | 10 ms | — |
| `release_after_score_boundary_ms` | **0** | 10 ms | — |
| `tail_f0_persistence` | **0** | 0.0333 | — |
| `terminal_mel_persistence` | 1.43e-04 | 0.0387 | **ε の約 1/270** |

mel 軸のずれは校正刺激（2.97e-07）より **約 500 倍大きい**。本番セルの方が長く、
P-ANCHOR はフル譜面レンダなので、最下位ビットの差が蓄積する量が違うためと見られる。
それでも ε より 2 桁以上小さく、**どのセルの結論も動かない**。

「完全一致セル 0/360」なのは mel 軸が全セルで僅かに動くためで、**4 軸すべてが
バイト一致したセルは無い**が、**ε 基準ではすべて再現している**。

群単位の結果は [`probe_0b_groups/`](probe_0b_groups/) に入れた（初回のものは
作業ディスク上にしか無く失ったため、以後は git に入れる）。

## 4. pin 意味論の訂正

私（実装側）が前提にしていた「checkpoint を pin すれば波形がバイト再現する」は
**実測で不正確**だった。正しい対応は:

| pin | 保証するもの | 再 export を跨ぐか |
|---|---|---|
| checkpoint / config / canon / vocoder の sha | **入力の同一性** | ✅ 跨ぐ |
| `samples_sha256` | **同一プロビジョニング内の完全性**（改竄・破損検出） | ❌ 跨がない |
| **`reference_output` の再測定（`\|Δ\| ≤ ε`）** | **結論の再現性** | ✅ 跨ぐ |

`samples_sha256` は科学的に必要な水準より**厳しすぎる** pin だった。捨てはしない
（セッション内の完全性検査として有効で、実際 B-1 の manifest 照合で機能している）が、
**「再現できた」の判定基準は `reference_output` の再測定に置く**。

なお `wav_sha256`（容器）は更に弱い — libsndfile が PEAK チャンクへ**書き出し時刻**を
入れるため、同一セッション内の再書き出しですら一致しない（2026-08-21 実測済み）。
強さの順は `reference_output 再測定` > `samples_sha256` > `wav_sha256`。

## 5. 環境ずれ 4 件（同じ形で繰り返す）

コンテナ再構築のたびに、依存解決が**宣言 pin から静かに離れる**:

| # | ずれ | 危険度 |
|---|---|---|
| 1 | 測定側 numba 0.67.0（pin は 0.66.0） | **高** — `librosa.pyin` が SIGSEGV する組み合わせ。pin 違反のまま測定が走りうる |
| 2 | export venv の numpy 2.4.6（DiffSinger は numpy<2） | 中 — export が壊れる |
| 3 | export venv に `lightning` 欠落 | 低 — 即座に落ちる（安全側の失敗） |
| 4 | メイン interpreter に `onnxruntime` 欠落 | 低 — 即座に落ちる |

**4 番の復旧で render_stack の記帳が効いた**: manifest に
`onnxruntime 1.29.0` を書いてあったので、最新版ではなく**記録された版**を入れて
判定できた。これが無ければ「最新版で測って不一致 → 決定論の破れ」と誤診していた。

対策は `provision.sh`（17 資産 + DiffSinger + 測定スタック + export venv）と
SessionStart hook（`ANALYSIS_STACK_PIN` の復元）に集約済み。
