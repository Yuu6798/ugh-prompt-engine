## 2. 順序規律（§12-0-C2）の実測記録

「候補空間を**校正を 1 度も走らせる前に**コミットして pin する」は運用規律であって
機械強制ではない、と設計書自身が但し書きしている。本 PR での実際の順序:

1. コミット `97c732f` — 事前登録 3 点のみ（コードは 1 行も無い）
2. その後に `run8/s7_b1_calibration.py` を実装し、校正を初回実行

機械側の照合として、`trf_measurement_spec.json` の `prereg_pins` が実ファイルの
sha256 と一致することをテストで固定した（`test_spec_pins_match_the_prereg_files_on_disk`）。
これは「pin した JSON をすり替えていない」ことの検査であって、**コミット時刻の
前後関係そのものは依然として git 履歴でしか検証できない**（設計書の但し書きどおり）。

## 3. B-1 の結果と、**凍結を 1.0 と名乗らなかった理由**

4 軸とも候補が生き残り `frozen` になったが、**1.0 ではなく `1.0-rc1`**（`freeze_status: candidate`）
として出した。理由は 2 つで、どちらも成果物を良く見せない方向の記述である。

### 3-1. 校正音源が合成刺激のみ（vocoder 出力を 1 本も通していない）

§12-0-A-1 の校正条件（clean terminal `/ri/` / `/i/` / `/N/`・forced long-tail・
配分摂動・無音・gain 対）は**音素名で書かれている**が、§12-0-A-3 の選択基準は
すべて測定側の物理性質（再現性 / gain 不変性 / 無音で 0 / 制御摂動への単調応答 /
プロセス間再現性 / 数値安定性）である。後者は既知の正解を持つ刺激を要求するため、
**決定論合成刺激**（`s7_b1_calibration_set.json` の 13 本）で校正した。checkpoint を
必要としないので GPU $0 で誰でも再現できる一方、**実レンダの artifact を一度も
通していない**という限界がそのまま残る。既存の実レンダ音源（`planb/results_pb0` の
fault / clean excerpt）は **run5/6/7 の良し悪しそのもの**であり、§12-0-A-1 が
「本番仮説の答えを見て測定器を選ぶ経路を構造的に断つ」と定めた対象なので使わなかった。

### 3-2. 6 つの hard requirement が候補を 1 つも落とさなかった

12 候補（時間 / f0 軸）と 3 候補（mel 軸）が**全て全要件を通過**した。つまり
今回の校正セットは候補間を弁別しておらず、勝者は順位付けキー
（gain 誤差 → 無音残差 → 制御摂動への応答マージン → hop → window → 名前）で
決まっている。**「物理的に一番信用できる測定法を選ぶ」という選択が実質的に
働いていない**ので、有料 Gate の物差しを 1.0 と称するのは実態より強い。

刺激を足せば弁別力は上がるが、**校正セットも事前登録物**なので黙って増やさない
（§12-0-C2 と同じ規律。増やすなら memo 改訂として記帳する）。

### 3-3. 事前登録の改訂 1 件（記帳）

初回実行で、順位付けが `monotone_min_step` の **1e-16 の浮動小数点差**
（`0.13333333333333341` vs `...30`）で決まっていることが判明した。これは物理量では
なく BLAS / numpy ビルド間で安定しない。`s7_b1_selection_rule.json` に
`ranking_among_survivors.numeric_precision`（比較前に 9 桁へ丸める）を追加し、
`amendments` として次を記帳した:

- 何を足したか / なぜ足したか（float ノイズの大きさから決めた。候補の勝敗からは決めていない）
- **改訂前の勝者 4 件**（改訂で何が変わったかを外から検算できるようにするため）
- 候補・刺激・要件・許容差・キー順は 1 つも足していない / 消していない / 並べ替えていない

## 3-6. `ANALYSIS_STACK_PIN` 違反の実測（bot P1 から派生した自己申告）

宣言 pin の検査を実装して初めて分かったこと: **初回〜3 回目の B-1 実行は
`numba 0.67.0` 上で走っていた**（宣言は `0.66.0`）。repo にはまさにこの組合せについて
「numba 0.67.0 × numpy 2.4.6 は `librosa.pyin` が SIGSEGV・0.66.0 で解消」という
実測記録がある（`scripts/run5_bootstrap.py` の `ANALYSIS_STACK_PIN` 注釈）。
本セッションでは SIGSEGV は再現しなかったが、**宣言と違うスタックで測った値を
「宣言 pin の産物」として記帳しかけていた**のは事実である。

対応: `numba==0.66.0` をインストールして**宣言どおりのスタックで B-1 を測り直し**、
`verify_analysis_stack()` を測定前 fail-closed（`--probe` の独立プロセス側も同じ検査）
として実装し、観測版を `trf_measurement_spec.json` の `analysis_stack.observed` に記帳した。

**測り直しの実測差分**: `numba 0.67.0` で作った版と `0.66.0` で作った版を比較すると、
**`prereg_pins` と新設の `analysis_stack` 以外は全キーが一致**した（`reference_output` も
4 軸すべてバイト一致、選定候補も 4 軸すべて同じ。pyin を選んだ
`release_after_score_boundary_ms` を含む）。つまり**今回の数値は numba 版に依らなかった**。
それでも検査を入れる理由は変わらない — 一致は**測ってみて分かった結果**であって、
記帳の時点では「宣言と違うスタックの産物を宣言 pin の産物として書く」ことになっていた。
今後 pin が動けば同じ幸運は保証されない。
## 4. 凍結された測定仕様（`1.0-rc1`）

| 軸 | 単位 | 選定候補 | ε | ε の内訳（floor / repro） | 生存候補数 |
|---|---|---|---|---|---|
| `excess_tail_voiced_ms` | ms | `B_rms_autocorr_gate\|win100\|hop5` | 5 | 5 / 0 | 12/12 |
| `release_after_score_boundary_ms` | ms | `A_pyin_voiced_flag\|win100\|hop10` | 10 | 10 / 0 | 12/12 |
| `tail_f0_persistence` | ratio (0..1) | `B_rms_autocorr_gate\|win100\|hop5` | 0.0166667 | 0.0166667 / 0 | 12/12 |
| `terminal_mel_persistence` | ratio (>= 0) | `M1_1024_256_80` | 0.01935 | 0.01935 / 0 | 3/3 |

ε はすべて**測定側の性質だけ**から出している（`ε = max(numerical_floor,
reproducibility_bound)`。`numerical_floor` = 選定候補の hop 長 or 終端窓のフレーム数の逆数、
`reproducibility_bound` = 同一プロセス反復 + 独立プロセス反復の最大差）。
本番ラベルは 1 件も参照していない。

**裁定は `z'` で行うが ε は生単位**なので、B-2 側で換算規則
`eps_z = eps_raw / (1.4826 * MAD_group)` を凍結した（z 化に使う定数と同一で、
新しい自由度を導入しない。MAD は本番集団から出るので数値は PR-2 で当てる）。
