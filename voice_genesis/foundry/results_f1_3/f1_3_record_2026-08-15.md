## 1. 実装決定

### 1.1 donor_bank.py: `DonorUnit` スキーマ拡張（F1.3-A item1）

`overlap_frames: Optional[int] = None` / `preutterance_frames: Optional[int] = None`
を追加した（既定 `None` = 情報なし。`donor_bank.py`/`donor_bank_lab.py` はこの
デフォルトのまま unit を作るため後方互換）。`donor_bank_utau.py` のみ実値
（`round(overlap_ms / frame_period_ms)` / `round(preutterance_ms / frame_period_ms)`）
を設定する。overlap が負値（一部行で観測されうる符号付き表記）はクランプして
0 とし件数を record する（`n_negative_overlap_clamped`）。preutterance は本 F1.3
では**保持のみ**（消費未実装。§5 Open Questions 参照）。

キャッシュキー: `donor_bank_utau.py` の pickle キー材料へ
`schema=f1.3-overlap-preutt-v1` のバージョンマーカーを追加した（スキーマ変更後の
新フィールド無し旧 pickle との衝突を回避。単体テストで新旧キー非衝突を検算済み）。

### 1.2 joins.py v2: true overlap-add（F1.3-A item1/2）

`overlap_add_concat(pieces, overlap_frames)` を汎用ヘルパーとして新設した
（`(sp, ap)` ペア列を実際に重ねて配置し、重なり区間を log-sp 線形 + ap 線形で
クロスフェードする。総フレーム数が overlap 分だけ短くなる = **タイムライン総尺の
重なり補正**）。`assemble_v2` はこれを使い、note 列を「フレーズ内で連続する run」
へグルーピングして run 内は true overlap-add で連結し、run 間（フレーズ間ブレス等）
は従来どおり gap を carry-forward で埋める。

overlap 長は選択された donor unit の `overlap_frames`（oto 由来）を優先し、
`None`（vocadito/pjs）なら `DEFAULT_OVERLAP_MS=40.0`（frame_period_ms=5 で
8 フレーム）へフォールバックする（設計書 item2 のとおり）。

**[実装決定・record 記録]** 録音子音を前置した note（`consonant_source="recorded"`）
は、前置後の frame 列（子音クリップ + 母音核）全体に対し、選択された **母音核 unit
自身の** `overlap_frames` を接合長として適用する。子音クリップ自体は oto overlap
値を持たない（`ConsonantClip` に含めていない）ため、母音核の値を流用する近似で
ある。子音クリップの長さが overlap 長を下回る場合は `overlap_add_concat` 内部の
`min(overlap, prev_len, cur_len)` クランプが自動的に安全域へ収める。

v1 の `assemble`（単側ブレンド・`CROSSFADE_MS=30.0`）は設計書の指示どおり関数として
残置し、既存テスト（`test_assemble_crossfade_reduces_boundary_jump` 等）はそのまま
green。**render.py は `assemble_v2` のみを呼ぶ**（v1 の呼び出し箇所は無い）。

### 1.3 units.py: ループ境界 overlap-add（F1.3-A item3）

`_ping_pong_pad_v2(sp_seg, ap_seg, deficit, overlap_frames)` を新設し、往復
（forward/backward 交互）の各ピース間の継ぎ目に `overlap_add_concat` を適用した
（旧 `_ping_pong_pad` の硬い折返しは v1 として残置・テスト互換）。`resolve_unit_to_note`
は sp_base とループパッドの接続点にも同じ overlap-add を適用する
（`jn.overlap_add_concat([(sp_base, ap_base), (sp_pad, ap_pad)], loop_overlap_frames)`）。
loop overlap 長は `joins.DEFAULT_OVERLAP_MS`（固定 40ms）を流用する
（ループ折返しは donor 側の oto 情報を持たないため）。overlap-add で内部的に
縮んだ長さは、既存の `_force_length`（target_n_frames への強制トリム/末尾保持
パディング）がそのまま吸収するため、`resolved.n_frames == target_n_frames` の
既存契約は変更不要だった。`resolve_unit_to_note` に `frame_period_ms: float = 5.0`
引数を追加（既定値はプロジェクト全体で共通の 5ms、既存呼び出しは省略可）。

### 1.4 unit エネルギー正規化（F1.3-B item1）

`donor_bank.normalize_unit_energy(bank)` を新設した。各 unit の frame 範囲の
sp（母音核区間）の平均フレームパワー（`sum(sp, axis=1)` のフレーム平均）を計算し、
**bank 内 unit 平均パワーの中央値**を正規化先ターゲットとして採用する
（**[実装決定・record 記録]** 恒常的な絶対定数より bank ごとの典型レベルに自然に
合う・データ駆動・決定論）。各 unit の sp へ一様スケール `target/unit_level` を
乗算し（ap は変更しない・振幅非依存の比率量のため）、head/tail_log_bands を
正規化後の sp から再計算する（units.py の接合コストが正規化後の実レンダー値と
整合するように。単体テストで検算済み）。3 ドナーすべて（vocadito/ritsu/pjs）に
一律適用する（設計書本文が「各 unit」と донор非限定で書いているため）。
`render.py` は donor bank 構築の直後・unit 選択の前に呼ぶ
（`bank, energy_norm_stats = db.normalize_unit_energy(bank)`）。

### 1.5 振幅権威の一本化（F1.3-B item2）

`render.py` は最終波形 `y` に対し `performance.build_amplitude_envelope`
（フレーズアーチ + フレーズ末減衰 + note attack）を乗算方式で適用する
（`singer/render_song.py` の `amp_render` 適用パターンと同じ）。unit 由来の振幅は
§1.4 の正規化で spectral 形状のみへ縮退済みのため、これが最終波形の音量
ダイナミクスを決める唯一の経路になる（perf_genes.py 自体には振幅パラメータを
追加していない — 設計書の「唯一の権威 = build_amplitude_envelope + perf_genes」は
「(既存の) perf_genes と組み合わせて使う build_amplitude_envelope が権威」の意と
解釈した。§5 Open Questions 参照）。

## 2. 接合統計（実測、E2E 3 レンダー共通）

| レンダー | n_joins_applied | n_runs | overlap 平均(frame/ms) | overlap 適用値の分布(frame) |
|---|---|---|---|---|
| sakura × ritsu | 14 | 6 | 18.57 / 92.86ms | 20×11, 10×2, 20(混在) |
| umi × ritsu | 9 | 3 | 20.0 / 100.0ms | 20×9（全件同一） |
| sakura × pjs | 14 | 6 | 8.0 / 40.0ms | 8×14（全件 DEFAULT_OVERLAP_MS 固定） |

- **リツ**: oto overlap 実値（10〜20 フレーム = 50〜100ms）が使われている
  （`overlap_frames_applied` 実測値: sakura=`[20,20,20,20,20,20,20,10,10,20,20,20,20,20]`、
  umi=`[20,20,20,20,20,20,20,20,20]`）。`n_joins_skipped_short=0`（全 join が 2 フレーム
  以上で成立）。
- **PJS**: oto 情報を持たないため設計どおり固定 40ms（8 フレーム）へ統一。
- タイムライン総尺は overlap 分だけ短縮した: sakura×ritsu 28.425s（F1.2）→
  27.125s（F1.3・**-1.300s**）、umi×ritsu 12.415s → 11.515s（**-0.900s**）、
  sakura×pjs 25.950s → 25.390s（**-0.560s**）。

## 3. 正規化統計（実測）

| bank | n_units | target_power(中央値) | pre_variance | post_variance | 分散削減率 | gain range |
|---|---|---|---|---|---|---|
| ritsu（A3+F4 258 units） | 258 | 1.7362 | 1.1409 | 0.2707 | **-76.3%** | 0.360〜2.534（中央値≈1.000） |
| pjs（278 units） | 278 | 1.2367 | 2.5924 | 4.42e-32 | **-100%（数値誤差域）** | 0.106〜250.5（中央値≈1.000） |

- **[実測所見・record 記録]** PJS は分散がほぼ完全にゼロへ収束する（unit 間で
  frame 範囲の重複が無い設計のため、スケール適用が理論どおり厳密に効く）のに
  対し、リツは 76.3% 削減に留まる（完全にはゼロにならない）。原因調査:
  リツの unit 切り出しは実 oto.ini（VCV 連続音・messy な手作業アノテーション）
  由来のため、ごく一部のエイリアス間で母音核 frame 範囲が重複している疑いが
  ある（`normalize_unit_energy` は非重複前提で「後勝ち」的にスケールを適用する
  ため、重複区間があると片方の unit の post-level が理論値からズレる）。今回の
  実装では重複検出・警告は行っていない（設計書に明記の無い edge case。§5
  Open Questions 参照）。それでも 76% の分散削減は「収録包絡の持ち込み」を
  大幅に緩和する方向であり、耳判定で効果を確認する。
- PJS の gain 最大値 250.5 は 1 unit（無声区間が多く median power が極端に低い
  短い母音核）由来の外れ値。クリップ・下限は設けていない（設計書に指定が
  無いため。§5 Open Questions 参照）。

## 5. Open Questions（設計書に無い判断・要 User/Fable 確認）

1. **録音子音前置後の overlap 長の流用**: §1.2 のとおり、子音クリップ前置後の
   note に対して母音核 unit 自身の `overlap_frames` をそのまま接合長として使う
   近似を採用した。子音クリップ自体に固有の overlap 値を持たせる設計（例えば
   oto エイリアスの preutterance を子音クリップ側の overlap として使う等）も
   考えられるが、本 F1.3 では実装していない。
2. **リツの正規化後分散が完全にゼロへ収束しない件**（§3）: 実 oto.ini 由来の
   unit 間で frame 範囲の軽微な重複がある可能性を疑っているが、重複検出は
   未実装（設計書に指定の無い診断機能）。次段で `donor_bank_utau.py` に
   非重複 assertion / 警告を追加するかどうかは要判断。
3. **正規化 gain の上限クランプ**: PJS で gain 最大 250.5 倍という極端な外れ値が
   発生した（§3）。無声区間が多い短い unit の実測パワーがほぼゼロに近いことが
   原因。gain に上限（例えば 10 倍等）を設けるべきかは設計書に指定が無いため
   未対応（今回の 3 レンダーでは聴感上の破綻は確認できていないが、耳判定で
   確認されたい）。
4. **preutterance_frames の消費**: F1.3-A item1 は「保持」のみを要求しており、
   本実装も `DonorUnit.preutterance_frames` へフレーム値を格納するだけで、
   接合・配置ロジックのどこにも使っていない（record 記録のみ・§1.1）。将来
   preutterance を「note の実効開始位置を前倒しする」目的で使うかどうかは
   未定義のため、次段（F1.4 以降）で判断されたい。
5. **振幅権威の「+ perf_genes」の解釈**: 設計書 F1.3-B item2「振幅の唯一の
   権威 = performance.build_amplitude_envelope（フレーズアーチ）+ perf_genes」を
   「(既存の) perf_genes と組み合わせて使う build_amplitude_envelope が唯一の
   権威」と解釈し、perf_genes.py 自体には振幅パラメータを追加しなかった（§1.5）。
   perf_genes 側に独立した振幅微細構造（shimmer 等）を追加する意図だった場合は
   Fable の意図と齟齬がある可能性があり、確認されたい。
