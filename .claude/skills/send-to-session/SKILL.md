# send-to-session — セッション間メッセージ送信

`/send-to-session <宛先> <メッセージ>` で別セッションにメッセージを届ける。
宛先は **セッション名**（タイトル）または **セッション ID**（`session_...`）。
引数が欠けていたら会話文脈から補い、どちらも不明なときだけユーザーに聞く。

2026-08-08 のセッションで手動確立したフローの機械化。設計上の要点:

- 経路は 2 本。**稼働中の相手には SendMessage（直送）**、**アイドルの相手には
  Routine（poke トリガー）配送で起こして届ける**。直送が常に優先（軽い・即時・
  トリガー残骸なし）。
- ペイロードは**テキストのみ**（トリガー追記は ~64 KiB 上限）。JSON はメッセージに
  インライン埋め込みで送れる。ファイル本体は送れないので、ブランチに push して
  「`<branch>` の `<path>` を読め」と**参照を送る**（同一マシンのローカルセッション
  同士ならパスだけでよい）。
- 受信側からの返信経路は**自動では張られない**。返信が必要な用件では、メッセージ内で
  送信元セッションの名前と ID（`session_...`）を名乗り、返信手段まで明示する
  （送信元が稼働中なら SendMessage、アイドルなら同じトリガー配送）。返信が届けば
  本セッションにユーザーターンとして現れる。

## 手順

### 1. 宛先解決 — まず稼働中リスト

`ListAgents` を叩く（未ロードなら ToolSearch `select:SendMessage` も同時にロード）。
宛先名が載っていれば `SendMessage` で直送して**手順 4 の報告へ**（これで完了。
トリガーは作らない）。

### 2. アイドルセッションの探索

`ListAgents` に居ない場合:

- 宛先が `session_...` ID なら `get_session` で実在・タイトル・**状態**を確認する。
  ARCHIVED のセッションはイベントを受けられない（fire は成功風に見えても届かない）
  ので配送せず、unarchive して送るかをユーザーに確認する（人が意図的に閉じた
  セッションを勝手に起こさない）。ACTIVE 系なら手順 3 へ。
- ユーザーが宛先を **Cowork** と明言しているなら名前検索は徒労（一覧から除外・
  タグ検索もセッション内から不可）。ページングせず、ID の提供を求める。
- 名前なら `list_sessions`（`mine: true`, `limit: 100`）で探す。結果がインラインで
  返ればそのまま読む。大きくてファイルに退避されたら python で読む: `json.loads`
  できればタイトルを構造的に走査するのが第一候補（`"title":"([^"]*)"` の正規表現は
  エスケープ引用符や整形 JSON を取りこぼす）。パース不能な断片なら生テキスト検索に
  フォールバック。`"has_more":true` なら `"last_id"` を取り出し `after_id` に渡して
  次ページへ。**全ページ掃くまで「無い」と結論しない**（実測: 3 ページ ~280 件規模）。
- ヒットしたら周辺 JSON から `id` / `session_status` / ブランチを抜き出す。

全ページ探して見つからないときは、その旨と次の可能性を報告して終了:
Cowork セッション（`cowork-local`/`cowork-remote` タグ付きで一覧から除外。タグ検索は
セッション内から**不可**と実測済み — 試して無駄打ちしない）、別アカウント起点、
名前の記憶違い（近い候補タイトルを挙げる）。ユーザーが ID を持ってくれば手順 3 で
続行できる、と案内する。

### 3. トリガー配送（アイドルの相手を起こして届ける）

1. `create_trigger`: `name` は `send-to-session-<短い用件>`、`prompt` にメッセージ
   本文、`persistent_session_id` に宛先 ID。**cron_expression / run_once_at は
   両方省略**（poke 専用。スケジュールを付けると勝手に再発火する）。
2. `fire_trigger` で即時発火。
3. `get_session` で配送確認: `session_status` が IDLE → RUNNING に変われば着信処理
   開始。まだ IDLE なら間を置いて再確認する（1–2 回。`sleep` は使わず、報告文の
   下書き等の作業を挟んで時間を稼ぐ）。
4. **RUNNING 遷移を確認してから** `delete_trigger` で後片付けする。発火処理中の
   削除が in-flight のメッセージを落とさない保証はないため、確認前に消さない。
   再確認しても IDLE のままなら、トリガーは残置して「発火は成功したが相手の起動は
   未確認。トリガー <id> を残したので後で fire_trigger で再送可能」と正直に報告する
   （成功と断言しない）。

### 4. 報告

ユーザーに以下を 1 パラグラフ + 箇条書き程度で報告する:

- 宛先（タイトル / ID / ブランチ）と**使った経路**（SendMessage 直送 or トリガー配送）
- 配送確認の結果（相手の状態遷移）とトリガー掃除の完了
- 返信を依頼した場合: 返信はこのセッションに届く旨

## メッセージ本文の作法

- 冒頭に送信元を名乗る（リポジトリ名に加え、可能なら自セッションのタイトルと
  `session_...` ID。返信の宛先になる）。受信側は
  文脈ゼロで読むので、用件・背景・期待するアクションを自己完結で書く。
- **相手にさせたい作業範囲を明示する**。単なる共有・疎通なら「対応不要。受信確認の
  短い応答のみ」等と書き、意図しない作業の暴発（= 相手セッションのトークン燃焼）を
  防ぐ。宛先は Fable 等の高価なセッションであり得る — 起こすこと自体がコストなので、
  用件のない wake を作らない。
- 自セッションで拒否・ブロックされた操作を相手にやらせない（権限迂回の禁止）。
