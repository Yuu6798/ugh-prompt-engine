### Design Decisions

**1. scorer pin の overengineering を認識し、脅威モデル境界で打ち切った**

Codex の P1 は 14 巡目まで途切れず、すべて技術的に正当だった（キー貫通 → `.libs` →
distribution 所有権 → 非 wheel fail-closed → DT_NEEDED 包含 → LD_PRELOAD/maps →
pre-bind TOCTOU → audit hook → ldconfig PATH 注入 → RPATH context → exact cache path →
GIT_* env）。しかし**塞ぐたびに「その隣の実装細部」が出る構造**で、しかも
「env/PATH/site-packages を能動的に制御できる攻撃者」への防御という、この計器
（ローカル完結・LLM 不要の研究用ツール）の脅威モデルに対して過剰だった。

User の指摘（「オーバーエンジニアリングになってるわけだよね？」）を受けて認め、
**`docs/DESIGN_M2_extraction_accuracy.md` §6 に脅威モデル境界を明文化**:

- **守る**: 受動的ドリフト（別バージョン数値ライブラリ・wheel 外 BLAS・事前ロード・
  ビルド差）の **tamper-evidence**
- **守らない**: 能動的 env 制御攻撃者。同じ能力の攻撃者は測定 JSON を直接偽造できるため、
  scorer pin だけ完全防御しても迂回経路が残り費用対効果が釣り合わない

以降は「受動的ドリフトの実装漏れ = 塞ぐ / 能動的攻撃者の残余経路 = 境界として反論
resolve」で振り分け、最終的に User 決裁で**レビュー対応そのものを打ち切り**（17・18 巡目
P2 は後続 issue 送りとして返信+resolve のみ）。

**判断の失敗として記録すべき点**: Fable の職務は「採否判定」なのに、技術的に正しい P1 を
reflexively に採用し続けた。**「技術的に正しい ≠ この計器の脅威モデルで採用すべき」**の
線引きは、14 巡目ではなく **9〜10 巡目には下すべきだった**。

**2. 敵対的セルフレビューを 4 弾実施し、各弾で観点を変えた**

「P1 が出るうちはマージしない」方針下で、Codex より先に同型を潰すため Opus に委譲:

| 弾 | 観点 | 検出 |
|---|---|---|
| 第一弾 | 縦の深掘り（場所/時点/被覆/実行時構成） | 12 穴（H1-H12・P1 級 7） |
| 第二弾 | 第一弾以降に追加した**新機構**（audit hook 等） | 4 穴（H13-H16） |
| 第三弾 | **宣言 vs 実装のギャップ**（docstring は守ると言うが実装は見ていない） | 1 穴（H17）+ acknowledged-boundary 4 件 |
| 第四弾 | ELF/subprocess 実装細部 | 3 穴（H18-H20） |

**第一弾 H1 の副産物**が特筆に値する: 閉包の完全性テスト（fresh subprocess の import 集合
⊆ 宣言集合）を実行可能テストとして入れた結果、**静的 grep では見えなかった
`charset_normalizer`**（scipy の array_api_compat → numpy f2py の遅延 import 経由）を
実行トレースで検出。「手書きリストは必ず負ける」問題への構造的対策が初回から効いた。

**第三弾で残穴が 1 件に枯れた**（12→4→1→3）ことは、先回り戦略が機能した証拠。ただし
第四弾で 3 件出たのは、13 巡目の fix 自体が新しい攻撃面を作ったため —— **穴を塞ぐ新機構が
新たな穴を生む**という追いかけっこの構造そのものは最後まで解消しなかった。

**3. CI 失敗 3 連続は、すべて「テスト側の環境依存前提」が原因だった**

| コミット | 失敗テスト | 原因 |
|---|---|---|
| `f391b15` | `test_reverification_refuses_when_stack_cannot_rerun` | pre-bind 検査が CI の shared-build CPython `libpython3.x.so` / システム C ライブラリ（libbz2/liblzma/libuuid/libz）を許容クラスに持たず誤 fail-closed |
| `0908870` | `test_require_unchanged_since_load_tolerates_optional_absent_to_present_transition` | 「load 時点 threadpoolctl は absent」というローカル限定の前提を固定 assert |
| `3b35473` | 同上（別経路） | **16 巡目の私の修正が新しい回帰を生んだ**（下記） |

User の問い（「CI やテスト条件がおかしい可能性は？」）は的確で、**プロダクトコードのバグ
ではなくテスト設計の脆さ**が主因だった。実行環境の ambient 状態（何が既に import 済みか・
どのライブラリがロード済みか）に依存する assert が多く、CI と実測機で揺れる。

**4. 16 巡目の自分の修正が回帰を生んだ（最も重要な失敗記録）**

Codex 16 巡目 P2-A（「instrumentation-only import を scorer closure から除外せよ」）に対し、
`_numeric_runtime_config()` の**呼び出し順序変更**（category loop 完了後・pin 確定後へ移動）
で対処した。これは子プロセス側の presence だけを変え、**評価器プロセス側の再計算は変え
なかった**ため:

- 測り直し子プロセス: pin 時点で threadpoolctl 未 import → `__absent__`
- 評価器プロセス: `_ensure_scorer_optional_closure_observed()` 後に別経路で import 済み → `present`

が**恒常的に食い違い** fail-closed する回帰が CI で顕在化。根本原因は
`_ensure_scorer_optional_closure_observed()` が「`mir_eval.melody` を import すれば optional
の participate が決定論的に確定する」を前提とするが、**threadpoolctl はその連鎖に乗らない**
（本ハーネスの instrumentation だけが import する）ため前提を満たさないこと。

最終修正（`128b405`）で run 側にも同じ観測を入れて子/評価器の presence を揃えた。
**技術的により正しいのは「threadpoolctl を閉包から外す」**（scoring 経路から import されず、
presence が instrumentation のタイミングを測ってしまうため）だが、テスト 15 箇所以上の
整合が必要で検証に 4 時間以上かかるため、CI green を優先して最小修正を選択した。

   assert が多数あり、CI と実測機で揺れて 3 回連続の CI 赤を招いた。環境非依存の不変条件へ
   書き換える方針を横展開すべき。
