    ただし量がジャンルで割れ単一補正係数不可（#111 の符号反転主張は n=3 で量差へ精緻化）
  - DR（real↑: +6.8 / +5.9 / +3.6）= Suno コンプ
- **Phase D ルール再設計（#115）= collect-all + 緩い intersection match を利用**。追加は
  Suno の match を壊せない（真の回帰面は extract 出力 context を pin する test_semantic_layer の
  厳密等価）。判別軸は manifest 実測 gap から:
  - rock 下限 brilliance 0.117→0.105（grunge HSB 0.108 捕捉）
  - **edm vs rock を sub_bass で分離**（rock≤0.048 vs edm≥0.055）= 今日の最重要発見。

- Codex P2 を計 4 件対応（#112 baseline 混入 / #114 brilliance 検定の overlap・delta 比較 / #115

### 追加プローブ — orchestral 課題の克服可能性を手持ちデータで一次調査（ephemeral 保全）
セッション後、ユーザー問い「課題は克服できそうか」を受け、手持ち（今日アップロードの本物管弦
FLAC が disk 残存 + repo 同梱 synth_01..05）で **採譜軸の分離可能性**を一次測定。包絡では分離
不能（harmonic で ano 0.969≈synth 1.0）だが、**採譜層で clean gap を確認**:

| グループ | chord_events | uniq和音 | 和音変化 | onset_density | harmonic |
|---|---|---|---|---|---|
| ORCH ano（最難）| 31 | 10 | 29 | **2.34** | 0.969 |
| ORCH holst | 22 | 7 | 11 | **3.93** | 0.836 |
| synth_01 slow_pad | 4 | 3 | 3 | **0.15** | 1.0 |
| synth_02–05 | 4–6 | 3 | 3 | **0.11–0.17** | 1.0 |

**所見**: onset_density（管弦 2.3–3.9 vs synth 0.1–0.2 ＝15–25× 重なりゼロ）と 和音変化数
（11–29 vs 3）が最強の分離軸。包絡で synth と同一の「あの夏へ」も onset_density で明確に分離。
→ **orchestral 対応は学習モデル不要で既存決定論フィールド（onset_density + 和音活動）を
第二判別軸に足す筋が本命**。克服可能性は高い。**留保**: n=2・synth は単一 pad/pulse の「おもちゃ」
で busy synth 曲は onset 上がりうる（ただし危険域 thin dark pad は低 onset で分離側）・chord_events
は密管弦で over-segment 気味（方向は頑健）・melody_contour はパース不発で本調査で精緻化要。
次 Design Memo は「onset_density/chord 活動を orchestral 第二軸に」を本物 n≥3 + 多様な synth で
分離度検証する設計から。

### Design Decisions
- **North Star を「測定器でなく楽譜（実用物）」に確定**。3 PR ロードマップは PR2/PR3 が検証・
  計測寄りで、「楽譜→演奏」コンパイルループが forward work（M5）に追い出されていた。だが調査で
  **コンパイル脚は既存**（`compose/prompt_renderer.py` の `ExternalPromptAdapter`＝楽譜→外部
  生成器プロンプト、`perform/performer.py` の決定論 performer＝楽譜→音声）と判明 → ループを
  閉じる **PR1.5（control_profile-aware compile）を PR2 の前に昇格**。
- **決定論 vs 非決定論は「緊張」でなく「層」**。物理層（PhysicalRPE）＝保証＝決定論（今固める）、
  意味層（SemanticRPE）＝助言＝非決定論探索（CLAP 等 OSS 学習センサー）。ユーザーは「探索/
  アドバイザー役の非決定論は否定しない、特に意味層読解には必要」と明言。**ただし `CLAUDE.md` の
  LLM-free 契約に従い、意味層読解は CLAP 等 API キー不要・ローカル OSS 学習センサーに限定し、
  API ベース LLM は out of scope**（採用には契約見直しの escalation）= Codex P2 #1 で是正。
- **多生成器は Suno ルート確立後**。1 本を端から端まで通して初めて抽象化の seam が分かる。
  2 本目の作業は遅らせるが、control_profile の生成器キー構造は今から保ち、PR1.5 で backend
  descriptor の seam を名前で引く（Suno 癖を直書きしない）。
- **音源バッチ運用**: 人手律速タスク（acoustic/K3/seed）が design-ready で複数同時になったら 1
  セッションに束ねる、は現時点 acoustic 単独で効き薄 → 頭の片隅メモに留める。
