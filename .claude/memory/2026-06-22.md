### Design Decisions
- **代行アップロードの transport 限界を正直に切り分けた**: Google Drive MCP の `create_file` は
  base64 をインラインで tool 呼び出しに渡す仕様で、3.7–4.8 MB の mp3 は 1 本でも base64 化すると
  100万トークン超 → 出力/コンテキスト制限で**直接アップロード不能**。`read/download` も同様で
  Drive 側 sha256 検証も不可。→ 不能を隠さず、代わりに **4 本を manifest id 名へ整えて
  SendUserFile で返送 → ユーザーが Drive へドラッグ → 私が Drive 側を search して `drive_file_id`
  を回収・byte-size で provenance 照合**、という橋渡し方式を採用。
- **content-addressing を厳守**: アップロード前に全 7 本の sha256 を manifest と照合（upload-only
  4 本＝astral/expA/expB/expC が完全一致、既存 3 本は drive_file_id 既存、wafu は未取得を確認）。
  Drive 側は読み取りで sha256 取れないため **byte-size 完全一致**で provenance を担保。
- **wafu_jungle_174 はエントリ削除でなく `excluded: true` 注記**: docs が measured/sha256 を参照
  しており削除すると orphan 参照になるため、非破壊の除外を選択（screen 記録は保持）。
- **bot P2 を loader 修正で根本対応**: `excluded: true` がメタデータ止まりだと `fetch_corpus.py`
  が依然 not_found 計上し「7/7 完結」が loader レベルで偽になる、という指摘は正当。
  `resolve_manifest` で excluded を sha256 解決前に `reason:"excluded"` 分類し materialization/
  unresolved から除外、`status_report` で `excluded` を別計上。silent drop しない透明分類とし、
  回帰テストを追加。実 manifest で `wafu -> excluded` / unresolved 非計上を実証。
