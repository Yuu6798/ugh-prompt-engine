### Design Decisions

**1. 契約の逐語実装に徹し、曖昧さは fail-closed 側で解消した。**
設計書が明示していない 2 点だけ判断が要り、いずれも**厳しい側**に倒して PR 本文で
開示した: (a) `determinism_failures` を evaluable pair に絞らず全件数える（§10 の
「1 件でも失敗したら gene 全体を FAILED」の字義どおり）、(b) 別プロセス再計算が
異常終了したとき空辞書を返さず `S3Stop` で停止する（空を返すと全 pair が
「別プロセス不一致」に化け、**決定論違反と実行失敗が区別できなくなる**）。

**2. 凍結 pin 照合を入れたら 8 pair 全件が不一致になり、原因はラベルだった。**
Codex の P1 指摘（「再構築入力を manifest の `identity_sha256` /
`performance_sha256` と突き合わせていない」）を採用して照合を実装したところ、
**8/8 が不一致**。追跡すると素材の差ではなく `source_id` ラベルの違いで、
`pr_attribution._rebuild` は `"ritsu"`/`"pjs"`、凍結走行の `pr_run` は
`"ritsu_singing_db"`/`"pjs_corpus"` を使う。`content_sha256()` が `source_id` を
先頭にハッシュするためダイジェストがずれていた。`dataclasses.replace` でラベル
だけ差し替えると pin と完全一致 → **sp/ap/f0 は byte 同一で測定値そのものは有効**。
ただし照合が無い状態では素材が差し替わっても検出できず、**§20-2「source SHA
不一致」が実質無効だった**のは指摘のとおり。`planb_real` は read-only 制約
（§14）があるので `_rebuild` は直さず、**S3 側で自前に組み立てて pin を再現**する
形にした（`RITSU_SOURCE_ID`/`PJS_SOURCE_ID` はラベルの**表明**＝不一致なら停止）。

**3. P4 が B0 を見ていなかった（偽 SUPPORTED の具体経路）。**
P3 は「B0 との比較」なので、B0 が非決定論なら比較自体が再現しない。gene 条件
だけ安定していれば SUPPORTED が立ち、S3 PASS まで通りうる。B0 の recorded /
same-process / cross-process も見るようにした。

**4. 「全数掃討」の終端宣言を早すぎるタイミングで出し、次の巡で訂正した。**
第 3 巡で来歴ファミリを「入口を全数掃討した」と宣言したが、第 4 巡で
`identity_ap_scale` が未検証のまま残っていると指摘された。**`context_phones` と
完全に同型のフィールドで、直前に自分で塞いだばかりの穴の隣**だった。宣言を
訂正し、以降は打ち切らず「新しい具体経路を示す指摘は巡数に関わらず採用」へ
方針変更した（CLAUDE.md bot レビュー運用の実害基準）。**教訓 = 「掃討した」は
同型フィールドの列挙を実際に取ってから言う。**

**5. 前提が誤っている指摘は採用しなかった（実測で反証）。**
第 5 巡の「squash で pin が検証できない」は
`git merge-base --is-ancestor 7366a94 1b345f6` が 0 を返し（＝ancestor）、
`1b345f6^` が `7366a94` そのものだったので **squash ではない**と反証（レビューは
squash プレビューの合成 commit を見ていたと思われる）。加えて本リポジトリは
merge commit 運用（`98cce91 Merge pull request #294`）でブランチ commit は main に
残る。ただし「commit ID はその object を持つクローンでしか照合できない」という
一般論には実害が残るので、**別の形で塞いだ** = `code_state.source_digest`
（判定に関与する 4 モジュールの内容 digest。git object に依らず照合可能）。
